## 0. Verdict in five lines
1. **One exact branch is cheap [K code -> P].** The 36 GDN states are 3.15 MB each (fp32 48 x 128 x 128), 113 MB in all; the verify kernel keeps each thread's 4 state floats in registers across the rows and reads and writes the state once per call, so a row costs ~0.06 ms per check of recurrence [K R-21] and the state traffic ~1 ms per scan. A **leaf sibling** fused at step p (the parent's state is in registers right before the chain's row p is applied) costs no state bytes and no launch: ~0.06 ms per check plus its row. A **deeper branch** needs no materialized state either: at the fork step the parent's state is in the kernel's registers, so the branch's rows run on a register copy (4 floats per thread) before the chain's row p is applied, depth-first, and the copy is discarded; zero state bytes, ~0.06 ms per branch row per check (section 1b). The boundary-capture form (113 MB written at p, 113 MB read by a branch scan, ~1.0-1.2 ms per fork) is the fallback if that kernel variant is not built. Both are bitwise by construction (REF2's INV-T: rows from a state == the 1-row steps). Attention: the branch's rows need their keys contiguous after their ancestors, which a scratch copy of the current 512-key bucket with the branch rows at the chain's slots gives (<= 1 MB per layer, 12 SDPA calls per fork, ~0.2-0.3 ms), bitwise under REF2b's row invariance [K R-62b]. The rest of a branch row is a chain row: experts 0.84-0.91 of a chain row's new experts [K M-10], ~1.0 ms at the mission-27 stack (1.6 beyond 16 rows with the dense tiles), and its drafted steps in lockstep with the chain (2.2 ms per step today, ~1.0 with the 4-bit head).
2. **What a rescue is worth, measured on the head's own ranks [K D-24 replay]:** at the cut chain's first miss, #2 or #3 holds the 125B's token 52-57 % of the time on chat, 63-77 % on math, 68 % on code (KWALL (b)'s 98.2 % is for mid rows at depth 1 along the true prefix; at a chain's first miss, any depth, it is these); the run that follows a rescued token (the continuation a branch could keep) averages **1.08-1.12 tokens on chat (zero in 45-46 % of rescues)**, 2.5 on mgsm, 3.2 on gsm and code. A hard position is followed by hard positions.
3. **The policies, at the floor engine (dense 17 ms, 1.0 ms per row to 16, 1.6 beyond, 0.3 per fork with the fused scan, 0.3 per leaf position, 2.2 per drafted step), tok/s against the cut chain, then halved [K replay, P]:** leaves (#2 + #3 at the first depth with p1 < 0.8): ifeval +3.2 % (+1.6), multi +1.4 (+0.7), code +0.3 (+0.2), gsm -0.3, mgsm -0.1; a continuing branch of 1 row: code -0.3, gsm -0.9, ifeval -0.3, multi -2.4 %; of 2 rows: -1.1 to -8.3; of 3: -2.4 to -14.3; chat's wide tree (top-3 at depth 1 with 3 rows each): +27 % kept at -20 % tok/s; the oracle fork placed at the chain's first miss with 6 rows: code +3.4 % (B16), gsm +5.0, mgsm -2.9, chat -11 to -13. **With rows and forks free** the bounds are: leaves +3 to +11 %, forks +3 to +9 %, chat's oracle fork still negative (its extra drafted steps). The realizable flag (p1 < 0.8) fires on 12 % of code depths, 25 % of gsm, 69 % of chat, with P(miss | flag) 49 / 45 / 68-72 %: half the branches are wasted on positions the chain gets right.
4. **Chat (55-58 % hard rows):** the cut chain keeps 2.40-2.58 tokens in 3.3-3.5 rows; leaves lift the kept to 2.67-2.82 (+9-11 %) for +1.6 rows, +1.4-3.2 % tok/s (halved +0.7-1.6); a wide tree lifts it to 3.04-3.13 (+21-27 %) for +9.5 rows and -23 % tok/s; even the oracle fork loses. The chat wall is the token after the hard one, not the hard one: the branch's continuation is 1.1 tokens because the next position is hard again. Chat's levers stay the drafter's accuracy at hard rows (NEXT_DRAFTER's AR head, coverage), the dense constant (50 ms today, 17 at the floor) and the draft step (2.2 -> 1.0 ms), not branching.
5. **The bet, EXACT track: no tree build; FAST track: R2 acceptance at the hard rows, which cashes the same top-3 information without rows (section 3b: code +5.5-8 %, chat +6.5-10 %, halved).** Exact branching is not the wall (a fork is ~0.3 ms with the fused scan, a leaf ~0); the wall is the economics: a rescue yields 1 + E[run] tokens, E[run] is 1.1 on chat and the miss is rare on code, so no placement and no row budget turns branches into more than +3 % (halved +1.6 %), and that only for leaves on chat. The boundary-capture branch (section 1) stays on the shelf for a drafter whose continuation after a hard token averages >= 3 tokens on chat; today's heads give 1.1. The cheapest test that could overturn this is MTP Head's D-24 harness with the leaf arm scored at the floor engine's costs (a CPU replay, 10 minutes), which is what tree_wall.py already is.

"Each branch needs its own recurrent state" is true and costs 113 MB written once and read once per fork: about 1 ms, not 50 MB per layer per node (that figure assumed one stored state per tree node; a branch needs one capture per fork point and none per leaf).

## 1b. Cloud task 14's input, answered; the register-resident branch (added 21:4x) [K code, P]
Cloud Fable (CLOUD_ANSWER_FASTMODE.md) put two claims to this mission. **(a) "A leaf at the first miss gains nothing, because the bonus token already is the target's argmax."** Half right: the leaf's own token is indeed free (the chain's miss row already yields the target's argmax at that position as the bonus), but a verified leaf row carries the target's logits conditioned on that token, whose argmax is the next token: +1 per hit. The replay counts exactly that (+1, never the leaf token itself), which is why leaves give +9-11 % kept on chat (2.40 -> 2.67) and +3 % on code, and +0.7-1.6 % tok/s after halving. **(b) "A continuing branch needs ~2.4 GB of state per node."** No design here materializes a state per node. The verify kernel (mlx_lm's gated_delta_update) holds the state in registers, 4 floats per thread (`float state[n_per_t]`, n_per_t = 128 / 32), and loops over the rows inside one launch; the state is loaded once at the start and stored once at the end. At the fork step p the registers hold S_(p-1) just before the chain's row p is applied, so a tree-aware variant copies them (+4 registers per thread), runs each branch's rows on the copy depth-first (the same per-row expressions: decay, kv_mem by simd_sum, delta, the rank-1 update, the output by simd_sum), discards the copy, then applies row p to the original. **State bytes per branch: zero; per branch row ~0.06 ms per check** (R-21's per-row recurrence cost: 1.19 -> 2.04 ms from keep 1 to 15 over 35 layers); the only state traffic is the call's existing one read and one write. The conv window of a branch row is its ancestors' rows (a 3-row gather); the commit replays the kept path from the pre-verify snapshot as it does today. The figure of ~2.4 GB per node is what a tree whose every node's state is stored would cost (16 nodes x 113 MB plus conv states and attention scratch); the boundary-capture form stores one state per fork point (113 MB, ~1 ms), and the register-resident form none. So the orchestrator's line ("below 1/5 of a full state read per check, else stop") is met at 0 %, and the rest of the mission applies: continuing branches of depth 1-3 under one alternative are priced in section 3 (forks at 0.3 ms: their 12 attention calls) and in the replay's "capture fork" column (1.2 ms). Attention stays the exact branch's only per-fork cost: the branch's keys must sit contiguously after its ancestors in the same 512-key bucket (R-62b certifies row invariance for contiguous valid keys, not for masked keys in the middle of a bucket), hence a scratch copy of the bucket and one SDPA call per layer per fork; a single tree-masked call is a FAST-track form (section 3b).

## 4. Why no design pays: the arithmetic [P on K]
Expected tokens from one fork = P(the chain misses at the fork) x P(#2 or #3 holds the token) x (1 + E[run after the rescue]). Chat: ~0.9 x 0.55 x 2.1 = 1.0 token for 2-8 rows and the continuation's extra drafted steps; code: 0.4 x 0.68 x 4.2 = 1.1 tokens for 8 rows (the oracle), 0.6 with the realizable flag. A chain row at the floor engine returns 0.3-0.4 tokens on code at depth 12-16 and ~0 on chat beyond depth 3 (which is why the cut stops at 3.3 rows); a branch row returns 0.1-0.25. Leaves return the most per row (+1 token when they hit, no continuation rows, no extra steps) and still add only +3 % on chat because they hit in 55 % x 57 % of passes and the pass's cost grows by 6 %. With rows and forks free the best policies gain +3-11 %, so the tree's ceiling is small before any cost is charged; at any real row cost it is 0-3 %. The GDN state is not in this arithmetic at all: at ~1 ms per fork it is 2-4 % of a check, and leaves need none.
