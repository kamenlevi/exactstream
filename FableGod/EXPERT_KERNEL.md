# EXPERT_KERNEL — why the 16-row expert kernel streams at 60-66 % of the machine, and what reaches 85 % (FableGod, mission 27, Mon 2 Nov 2026, 20:4x-21:1x EET)
**Checked by Leap's measurements, Mon 2 Nov 23:00: the op-bound model below doesn't hold.** About 12 arms (TABLE_350 N7-0..11, NAX-C, H-1, M27-P/C) show the kernel is latency-bound per simdgroup:
- NAX6 runs ~7 us per group at saturation, against ~4.2-5 us of bytes and ~4.6 us of ops.
- The matrix unit is ~57 % busy and DRAM ~53 %. Each group waits through codes -> decode -> two dependent ops -> epilogue.
- int8 ops at 1.55x the throughput gained 0 %. Prefetch was +11 % slower, loader/op split +35 %, fusion +1 %, other split-K counts +-3 %.
- So the inner structure is at its ceiling. What's left: fewer groups or fewer bytes (tier merge B with the NAX reference, the gate's union cut, H-1c's compact hybrid on FAST, wider checks).
- **Update 23:31 (Leap N7-13, quiet lock): the ceiling was the load pattern.** A fragment-native record layout (each expert / 32-row tile / quant group contiguous) makes NAX6 18.7 % faster at S 16 (17.1 % S 8, 18.2 % S 32), bitwise to NAX6. Each lane had been reading 24 B at a 960 B stride; the cloud auditor flagged it.

## 0. Verdict in five lines
1. **What the kernel pays for [K code + fit]:** NAX6 processes the check's (row, rank) pairs in groups of up to 16 that share one expert and one tier ((expert, tier) groups), and for every group it streams that expert's codes once (MSB-3 2.15 MB, plus LSB-1 0.77 MB for a 4-bit tier) and runs the full 16-row tensor-op set over them: 9,600 ops of 16 x 32 x 16 (4,800 of 16 x 32 x 32) for gate, up and down, whatever the group's pairs. Leap's eight real-layer points (layer 20, 4 traces x S 16 / 32) fit `ms per layer = 0.094 + 10.15 us x groups` with a 4 us residual; distinct experts and pairs do not enter. 3c fits `0.042 + 7.08 us x pairs`; groups do not enter. Per group at the probe's matrix-unit peak the ops take 7.32 us [K K-62e: kernels A + B at peak = 0.60 ms for 82 groups]; the group's 1.98 MB stream in 6.95 us at 284 GB/s [K k62p / bw_probe]. **The matrix unit's work on a padded 16-row tile costs the same time as streaming the tile's weights, to within 5 %.** With zero DRAM traffic the kernel still takes 0.70 of its 0.85-0.90 ms [K K-62e diag 3]: it is compute-bound.
2. **Why 60-66 % at every width [P on K]:** per group 10.15 us = the 7.32 us op set (72 %) + ~2.1 us of DRAM not hidden (the zero-DRAM run) + ~0.7 us of A-operand marshalling, chunk sums and barriers; plus 0.094 ms per call of six dispatches (GPU grouping, two row sums, A, B, the combine) = 1.3 us per group at 72 groups. Share of streaming = 6.95 / (10.15 + 1.3) = 61 %, the C2 figure (60-66 %). It is the same at 8, 16 and 32 rows because every term is per group and the bytes are per group too; the row count only changes how much of each 16-row tile is real: 1.7 / 2.1 / 2.6 pairs per group at S 8 / 16 / 32 on the 36 real captures, 64 / 57 / 49 % of the groups holding a single pair [K routing]. The decode (spread3 / spread8, ~1.5 integer ops per value, into threadgroup memory as uint4 operands) overlaps the ops fully [K nax_tput mode 1]; load latency is not the limit [K K-62c]; the ALU is not the limit; occupancy is bounded by kernel A's 20 KB of threadgroup memory per 8-simdgroup threadgroup [K code] but the kernel runs at 72 % of the op peak with it.
3. **The structural limit, proved from the two per-group numbers:** 85 % of streaming allows 8.18 us per group all-in, 6.9 us after the per-call fixed cost; the op set alone is 7.32 us. **At the probe's matrix-unit rate (1.3 G ops of 16 x 32 x 16 per second, 10.5 T MAC/s on 20 cores) no 16-row tensor-op kernel reaches 85 % at today's unions: the ceiling is the matrix unit's MAC rate on padded 16-row tiles**, not the ALU, not memory parallelism, not occupancy. The ceiling moves only if (a) the true peak is higher than the probe's (the probe ran one dependent accumulator chain per simdgroup on the 16 x 32 x 16 shape; Apple's "over 4x the peak GPU compute of M4 Pro for AI" implies 16-33 T MAC/s for 20 cores at 1.6 GHz [G from a relative claim]), (b) fewer op sets per byte (the tier merge: -15-17 % of groups; int8 operands if an int8 x int8 mode exists), or (c) work moved off the matrix unit for the groups that waste it (the hybrid). **The one measurement to run first (10 minutes of GPU):** nax_shapes.py's rates for 16 x 32 x 32 and 32 x 32 x 16 (it exists, 1 minute; NAX6 issues 16 x 32 x 32 ops but the floor was priced at the 16 x 32 x 16 rate), then nax_tput with 2 and 4 independent accumulators per simdgroup and operands held in registers; if the op rate rises, the floor above is too high by that factor. A Metal GPU-counter capture of one NAX6 call (the neural-accelerator utilization counter) would show the same thing directly.
4. **Designs (per 16-row check: byte floor 25.7 ms at 284 GB/s for 7.30 GB, today NAX6 41.9 by the fit / 43.2 measured, 3c 50.5-56):** **A NAX7** (bitwise = NAX6): the six dispatches as two, A marshalled once per simdgroup pair, a three-stage code pipeline, two column tiles per simdgroup: 35.1 ms (73 %) if the probe's peak is the peak, 25.9 (99 %) if the true peak is 2x; **B TIER-MERGE** (a new row-invariant reference: the 4-bit pairs as two products, 0.02 % of outputs move by one bf16 ulp [K numeric]): one group per distinct expert, -15-17 % of the op sets: 30.3 ms on NAX7 (85 %), 36 on today's NAX6 (71 %); **H HYBRID** (bitwise = NAX6 only if the tensor op's reduction is a fixed fp32 order the probe can identify; otherwise dead for exact mode): the 1- and 2-pair groups' gate / up on the SIMD ALUs in that order, down on the matrix unit: 29-33 ms (77-87 %); H + B 28.8 (89 %); **C INT8-A** (quality-defined; needs an int8 x int8 op mode, unproven): byte-bound; **D ALU-only**: H's limit case, 90 % at 16 rows only at 3.2 us per pair (2.2x better than 3c's arithmetic), 75 % at 32 rows. At 8 rows the same designs give 70 / 79 / 74-84 / 83 %, at 32 rows 74 / 88 / 78-86 / 91 % (section 4).
5. **The bet:** the probe first; it decides between two worlds. If the op rate is >= 1.6x the probe's, NAX7 alone (bitwise) reaches >= 85 % at every width and nothing else is needed. If not, the exact stack is NAX7 + H (77-87 %), and 85-89 % needs B under REF3-T; C is the quality-defined reserve. With the gate (pairs x0.48, union x0.58): the floor falls to ~15 ms, the fixed cost becomes 30 % of it, and NAX7's dispatch fusion is the first lever (-3.4 ms). On 350: the experts at 16 rows go 43 -> ~29 ms (-14) in the probe-peak world, ~26 at 2x; the floor-engine cycle (dense 15-18 + experts) 61 -> ~47 ms without the gate (205 -> 265 tok/s at kept 12.5) and ~34-37 with it (340-370): the expert kernel at ~85 % plus the gate is what puts 350 in reach; NAX6 with the gate leaves ~41-44 ms (285-315) [P on ROUTE_350's terms].

## 2. Why 60-66 % at every width, and what sets the ceiling [P on K]
Per group: time = 7.32 (ops) + 2.1 (exposed DRAM) + 0.7 (marshalling, chunk sums, barriers) = 10.15 us, against 6.95 us of bytes. The ratio is width-independent because (i) the op count per group is fixed by the weight count (one 16 x 32 x 16 op per 512 weights, 16 rows wide whether 1 or 16 are real), (ii) the bytes per group are the expert's record, fixed, and (iii) the fixed cost per call is spread over ~70-120 groups at every width. More rows per group (wider checks, budget routing) raise the share of real rows in each tile but do not change the per-group time; they lower the time per pair, which is why NAX6's gain over 3c grows with width (B3: 1.41 vs 3.03 ms per added row) while its share of streaming stays at 60-66 %.
What 85 % means: 6.95 / 0.85 = 8.18 us per group all-in; minus the fixed cost (1.3 us) = 6.9 us for the kernel's body, below the op set's 7.32 us. So at the probe's rate the family cannot get there even with the DRAM fully hidden, the marshalling free and the dispatches gone. Three things move the line: the op rate (if the probe under-measured the unit: its one accumulator chain per simdgroup, 16 x 32 x 16 ops only, operands rebuilt in registers), the op count per byte (the tier merge: -15-17 %; int8 operands: -50 % if a 2x int8 mode exists), and taking the 1-2-pair groups (57 + 20 % of all groups at S 16) off the matrix unit (the hybrid: their 12 % tile occupancy is where the waste is). Memory parallelism is not the limit (K-62c: prefetching the next group's codes gained nothing; the exposed DRAM is the start of each K chunk and the 2-stage pipeline, a 20 % term); the ALU is not (the decode overlaps fully); occupancy is bounded (kernel A's 20 KB per threadgroup) but the body already runs at 72 % of the op peak, so occupancy cannot be hiding more than the remaining 28 %, of which the exposed DRAM is most.
The one counter: the probe sweep above (10 minutes); or Xcode's GPU counters on one NAX6 call at S 16, which report the neural-accelerator utilization, ALU utilization and memory bandwidth per kernel: utilization near 100 % on the accelerator says the ceiling is the rate; well under it says NAX7 has room.

## 6. The structural statement, once
Per (expert, tier) group the matrix unit's 16-row op set (7.32 us at the probe's rate) and the group's bytes (6.95 us at 284 GB/s) are equal to within 5 %, at every check width and union, because both are fixed per expert record while only the share of real rows in the tile varies (12 % at S 16). A kernel of this family therefore runs at min(ops, bytes) / (ops + bytes - overlap): 50 % with no overlap, 100 % only with perfect overlap and perfect op efficiency; measured 61 % (72 % op efficiency, 2.1 us of DRAM exposed, 1.3 us of dispatches). 85 % needs the body under 6.9 us per group, below the op set itself. So: at the probe's op rate the ceiling is ~75-80 % (NAX7 + H exact), the op rate is the one unknown that could lift it (the 10-minute probe), and above that only fewer op sets (B, -15-17 %; C, -50 % if the mode exists) or fewer bytes (quality calls) change the line.
