# BOUNDARIES — the dense pass as a dependency graph, what its ~2,700 kernel boundaries really cost, what Apple's GPU and Metal / MLX allow, three bitwise designs (EXACT) and the strongest non-bitwise ones (FAST), with the floor on each track (Fable B, mission B2 + Kamen's two-track addendum, Mon 2 Nov 2026, 21:5x-23:0x EET)

Two first-class tracks (Kamen, 22:5x, via the orchestrator): **EXACT** = bitwise to REF2-T, the default; **FAST** = quality-defined, judged by task results (EvalSuite's same-scores test). Every design below is marked. Within FAST, two classes are kept apart because their quality questions differ: **FAST-K** (kernel numerics: a different but fixed reduction order, "exact under its own numerics", rel rms ~1e-3, certified once as a new reference the way REF2-T was) and **FAST-Q** (quantization: tokens flip on a measurable share of rows, judged by scores and the map).

## 0. Verdict in six lines (1-5 EXACT, 6 FAST)
1. **The boundaries are not launches, and the GPU barely idles.** In the live warm 16-row check the GPU is busy for all but ~2.4 ms [K c0_live: wall 87.2 vs the pieces' GPU evals 83.9, 16-row probes, -0.1..+4.5]; inside an eager check the gaps between command buffers are under 5 us each and sum to 0.35 ms per 12 layers [K b5_gaps: 59 of 60 gaps per check < 5 us]; a dependent dispatch costs 1.3-1.6 us at the GPU, the same through an indirect command buffer, and an in-kernel grid barrier costs more, 2.0-2.5 us [K lithos / MoonShots]. So 2,700 launches are ~4 ms of gaps, ~1.5 of them on the critical path, not the ~26 ms gap to the floors.
2. **What the boundaries cost is the latency of the ~2,000 small dependent kernels between the ~700 big ones [P on K]:** each small kernel in a dependent chain is one or two memory round trips plus a wave ramp, 2-6 us in situ whatever its bytes (GDNX -6.4 us per removed kernel, D1-B -5.4, R-73 -3.6, R-09 X -2.4, GDNB ~0 [K]), ~8 ms per check (4-12), plus the big kernels' fills and drains in dependent chains (~2 ms). The GPU ledger: 34 ms of dense GPU = 14 of bytes floors + ~7 of GEMM rate and latency structure + ~3 of sequential structures (GDN's row steps, attention's key walk, the HC read's dependent pair) + ~8 of small-kernel chain + ~2 of fills [P]. Half of the check's kernels are on its critical path (708 of 1,384 at 12 layers; 62 % of the dependency levels hold one kernel; 38 % of kernels have slack) [K dag_check on R-11b's export].
3. **What Apple's GPU allows:** 20 cores [K]; ~1,536 spinning simdgroups stay co-resident in practice (half time out at 2,048) [K lithos], 128 x 256 threads in MoonShots' probe [K], but Metal guarantees neither co-residency nor forward progress (MSL spec; Apple's forum thread of June '26 has no answer; an M1 read stale data across threadgroups until `coherent(device)` was used) [K web]; device atomics exist (relaxed), cross-threadgroup visibility needs `coherent(device)` + device-scope fences (the spec-compliant barrier is 2.47 us vs 1.97 relaxed) [K lithos]; a GPU store reaches the CPU only at command-buffer end (~35 us before completion), so the CPU cannot sit inside a persistent kernel's loop [K publish.txt], while a kernel can spin on CPU-written memory (BigMoE's gate does, 48 times per check, with bounded spins and a timeout counter) [K ext]; a GPU-signalled MTLSharedEvent costs ~140 us, a CPU-signalled wait is free [K BigMoE]; MLX encodes on one concurrent compute encoder with barriers only on data hazards, commits every MLX_MAX_OPS_PER_BUFFER ops, has no indirect-command-buffer path, and its compiled graphs cut Python but not GPU time (B5c 5.04 -> 1.22 ms per 12 layers, bitwise; R-10 -0.7 ms) [K code / Leap]. The prior art (Hazy's no-bubbles megakernel, Mirage MPK, Cohere, FlashInfer) wins by overlapping the next op's weight loads with the previous op's tail through shared-memory pages and per-tile counters, on hardware that guarantees persistent-block co-residency; here the barrier is dearer than the dispatch, the measured phase-barrier megakernels gained +3 % and -2.7 % [K MoonShots], and the only transferable mechanism is tile-level dataflow inside one dependent pair, untested.
4. **Three bitwise designs, ms per check of GPU (bound, then halved):** **E1 fusion to the end** (the small kernels ~2,000 -> ~600: G1's GDN, D1-B's HC read + D5, a bitwise one-kernel replica of MLX's SDPA chunk set for attention, the MoE tail + combine + sort inside the experts' kernel, shared gate | up merged) **-7 / -3.5** (of which ~-3.5 / -1.7 is already in the GDN_PASS stack: do not double count); **E2 concurrency by construction** (the 38 % of kernels with slack placed beside the critical path by construction order and `mx.depends`, zero kernel work: GDN's z / b / a / gates under qkv, attention's k / v / indexer / mask / cache writes under q, the shared expert under the gate spin as SC2 did) **-2 / -1**; **E3 the tile-dataflow pair** (one persistent kernel for one dependent pair, 20-40 resident threadgroups, per-tile counters, the consumer's tiles starting as the producer's land; the same tile arithmetic, so bitwise) **-4 / -2 over the ~1,000 post-fusion boundaries, gated by one 20-minute pair test whose prior is 25 %**. **E4 the CPU side** (SB at 1 row, compiled per-layer dense chains) is 0 of GPU and -2.4 of wall at 16 rows, -7 at 1 row. Cross-layer weight prefetch is not proposed: GP6 showed a GPU weight stream re-read right after costs the same (the SLC does not hold it).
5. **The EXACT bet: E1 + E2, in that order, with E3's pair test run once.** Recount with Leap's measured D1-B (-1.3 to -1.8, not -3.9): the dense pass 34 -> **~26 expected, ~21.5 with every exact lever at its optimistic end**; E2 and E3 at their halves take the optimistic end to ~19-20. **The exact dense pass does not reach <= 17 ms per 16-row check.** The honest exact floor is **~19-21 ms** = 14 of bytes + ~3 of sequential structure + ~1.5-2 of residual GEMM rate + ~1-2 of the ~600 dependent kernels that no bitwise fusion removes. What crosses 17 on EXACT is per token, not per check: the 32-row check (the dense pass flat in rows: GDN +0.09 ms per row [K C0 / B3]).
6. **The FAST track (section 4F) is where the dense pass crosses 17.** The strongest non-bitwise designs, ms per check (bound / halved): **F1 reordered-sum GEMMs** (the HC read's two GEMMs and GDN's z / out_proj / small-N shapes with split-K over 4-8x more simdgroups and a fixed-order combine: the HC read runs at 99 us per read against 47 of floor because S4's one-simdgroup partitions walk 128 k steps [K D1-B]; row-invariant, so SD == AR holds under its own numerics) **-6.5 / -3.3**; **F2 the chunked GDN verify** (the 16 rows as one WY / UT chunk per head on the tensor units, the state read and written once as now; TRIED killed it only "for exact modes") **-1.5 / -0.8 on the check and -0.9 / -0.5 on the commit, -3.0 / -1.5 at 32 rows**; **F3 the fused invariant attention** (R-66's FATT16 with 2-4 simdgroups per head, no key buckets) **-0.5 / -0.3 beyond E1's exact replica**; **F4 HC8** (FAST-Q: 1.44 % of the map's rows flip, 0.00 % of sure rows; EvalSuite PASS with a lean) **-2.3 / -1.5**; **F5 the one-pass HC read** (HC_READ's D2) **-0.6 / -0.3**. The FAST dense pass: **~18.7 ms expected without HC8, ~17.2 with it; floor ~16-17 without HC8, ~14-15 with it** [P]. So **<= 17 is reached on FAST at the floor, or expected with HC8**, and never on EXACT at 16 rows. Both tracks publish; the 32-row check halves either per token.

### 1.2 True data edges vs ordering
- **Across layers: every edge is a true data dependency.** Layer L + 1's first HC read norms the four streams that layer L's MoE write produced; the MoE's HC read norms what the mixer wrote. There is no kernel of layer L + 1 whose inputs exist before layer L's last kernel finishes (TRIED: "cross-layer pipelining: layer dependencies forbid it"). The only cross-layer freedom is weight prefetch (section 4, E5) and the drafter / commit of the next cycle, which are not the dense pass.
- **Within a layer the chain is serial except at four places:** the GDN's z / b / a projections and the two gates (6 of 10 kernels off the path, ~0.5 ms per check of latency if serialized); attention's k / v / indexer projections, RoPE tables, mask build and cache writes (~20 of ~84); the shared expert against the router -> gate -> experts chain (3 kernels, ~1.6 MB each, ~10-15 us each); the z GEMM against the recurrence (MLX's post-order encodes them side by side by accident: GDN_PASS 2.3). The HC read, the recurrence, the SDPA chain, the norm -> out_proj -> write -> read sequence and the head are pure chains.
- **The graph, counted [K dag_check on `r11b_check.dot`, Leap's R-11b export of one 12-layer check on the Oct-27 engine: eager HC chain, MLX's quantized matmuls]:** 1,384 kernel-launching primitives (R-11b's count), **critical path 708 kernels (51.2 %)**, 854 kernels (61.7 %) on some critical path; 62 % of the 708 dependency levels hold exactly one kernel, 81 levels hold 4 or more (the attention chunks); 530 kernels (38 %) have slack: QuantizedMatmul 84 (k / v / a / b / shared / router), Multiply 79, AsType 54, Arange 48 (the mask and RoPE index builds), Matmul 26, the shared expert's compiled sigmoid 24. 54 % of kernels have exactly one kernel producer (chain links), 90 are joins. The drafter's graph is the same shape (595 kernels, critical path 278 = 47 %, 76 % of levels of width 1), which is why R-10 found it GPU-bound at ~500 small kernels. Today's engine has fewer kernels (REF2's padded 16-row GEMMs, GDNX, S4, R-70 / R-72 / R-73) but the same structure: the fusions removed chain links, not joins.
- **The ordering edges that are not data edges:** MLX's encode order (the graph's post-order from the outputs) and its barriers. The encoder is concurrent and inserts a barrier only before a kernel whose input was written by an earlier dispatch in the same encoder (`CommandEncoder::maybeInsertBarrier`, `prev_outputs_`, `ConcurrentContext`: device.h) [K code]; a barrier waits for everything before it, so an independent kernel encoded after a dependent one waits with it. The gate adds one ordering edge per MoE layer that is a true CPU dependency (the slot map lives on the CPU), and SB's async_eval every 4 layers adds 12 segment boundaries per check (no barrier: the next segment's buffers queue behind the previous ones).

Two readings of the same ledger: (a) **2,700 launches at 1.5 us are ~4 ms, and only the ~1,400 on the critical path count: ~2 ms** — the launch itself is not the lever, which is why the megakernel probes measured nothing; (b) **the ~2,000 small kernels cost ~8 ms because each is a dependent memory round trip that no amount of launch batching shortens** — the lever is to make them not exist (fusion into a neighbour's prologue / epilogue: their work rides inside a kernel that is already waiting on DRAM) or to take them off the critical path (concurrency). The fills and drains (~2 ms) are the only part a persistent dataflow kernel removes that fusion does not.

### 2.3 The wall ledger (the live loop)
Live warm 16-row check 87.2 ms = GPU evals 84.6 (experts 50.9 + dense 34.0) + ~2.4 of idle [K c0_live]; the cycle adds the drafter (~10-12.5) and the commit (~4.7) outside it. Exposed CPU: ~2.4 at 16 rows, 9.3 at 1 row (no SB), ~21 per check in the eager engine (B5). So the CPU side is a 1-row-check problem and a 350-cycle problem (at a ~50 ms cycle the same 8.5-10 ms of build per check must still hide under ~35 ms of GPU: it does, with SB), not a 16-row GPU problem.

## 3. What Apple's GPU and Metal / MLX allow, and the prior art
### 3.1 The hardware and the API [K unless marked]
- **Residency.** M5 Pro, 20 GPU cores (system_profiler) [K]. Metal allows 1,024 threads per threadgroup and 32 KB of threadgroup memory. lithos-metal's M5 Pro probes: 1,536 spinning simdgroups all resident (~77 per core, ~2,460 threads), about half time out at 2,048; one 384-thread threadgroup per core reaches 283-298 GB/s only with lane-interleaved 16-byte loads, 4 in flight [K MoonShots 33a]. MoonShots' own probe: 128 threadgroups x 256 threads co-resident through 400 grid barriers, every configuration completed [K gridbarrier.txt]. Residency of memory (MLX's `ResidencySets`, `set_wired_limit`) is a different thing: it keeps buffers wired, it does not schedule threadgroups [K resident.h].
- **Forward progress.** The MSL spec guarantees neither co-residency nor forward progress across threadgroups (MoonShots: "MSL 4.1 spec; OOPSLA'21 2109.06132 shows Apple GPUs violating occupancy-bound execution"); Apple's developer forum thread "Apple GPU forward progress guarantees for persistent-thread synchronization?" (June '26) has no answer from Apple; its poster reports that "synchronization schemes that rely on all threadgroups making progress eventually can become unreliable, while strictly local producer / consumer handoff patterns appear much more robust" [K web]. In practice: BigMoE's gate spins in a kernel on CPU-written lines with back-off, a timeout and a status counter that invalidates the pass (`bigmoe_spin`), 48 times per check, "no timeouts" in R-55's runs; the only recorded timeouts came with a thermal emergency pause (HANDOVER 172) [K]. The design rule: bounded spins, a timeout that fails loudly, and never more threadgroups than the measured co-residency.
- **Atomics and ordering.** Device-scope atomics (relaxed) exist; cross-threadgroup visibility of plain stores needs `coherent(device)` buffers and device-scope fences (MSL 3.2 section 4.8): the M1 forum case read stale data across threadgroup boundaries with `atomic_thread_fence(mem_device, seq_cst)` until `coherent(device)` was used [K web]; lithos priced the spec-compliant barrier at 2.47 us vs 1.97 relaxed [K]. There is no device-scope barrier instruction; `threadgroup_barrier(mem_device)` orders only within the threadgroup.
- **GPU <-> CPU.** A GPU store becomes visible to a spinning CPU thread only at command-buffer end, ~35 us before MLX reports completion, for any amount of traffic after the store [K publish.txt]: the CPU cannot be a participant inside a persistent kernel (MoonShots: "a persistent per-token kernel whose CPU loader learns the routing mid-kernel is not possible"). The other direction works: a kernel polls CPU-written memory (the gate). A GPU-signalled `MTLSharedEvent` releases a dependent wait ~140 us later; a CPU-signalled wait is free [K BigMoE]. So the residency gate must stay a command-buffer boundary with a CPU round trip per MoE layer, and a megakernel can span at most from one gate to the next (MoonShots M6b).
- **Concurrent dispatch.** MLX's Metal backend uses one compute encoder per command buffer with `ConcurrentContext` / `maybeInsertBarrier`: kernels are dispatched concurrently and a barrier is inserted only when an input was an earlier dispatch's output; fences (`MTLFence`) carry outputs across encoders; buffers are committed when `max_ops_per_buffer` / `max_mb_per_buffer` are reached (`MLX_MAX_OPS_PER_BUFFER`, `MLX_MAX_MB_PER_BUFFER`); `MLX_METAL_FAST_SYNCH` switches the cross-stream fence to Metal 3.2's fast mode (GP5: 0 % here) [K device.h, utils.h, fence.h]. From Python the only handles on order are the construction order (the post-order follows it) and `mx.depends` (SC2 used it to move the shared expert ahead of the gate spin: +0.9 % at S 4 [K TRIED]).
- **Indirect command buffers.** Metal has compute ICBs with per-command barriers (Metal 3, Mac2 family) [K web]; MLX has no ICB path (device.h: none) [K code]; lithos measured an ICB replay's dependent dispatch at the same 1.3-1.6 us [K], and R-11b priced the CPU side of a replayed ICB at ~2.1 ms per check against encode that already overlaps [K]. Nothing on the GPU side to gain; the CPU side is E4.
- **mx.compile.** Fuses elementwise chains into one kernel and cuts Python per op; usually bit-identical (R-73's compiled write: PASS; B5c: PASS) but not always (R-40 3t: the PLE gate's compiled sigmoid differs in the last bit; R-73: the stock spelling's reshape blocks the fusion); it does not change the big kernels [K].
- **The one measured persistent kernel on this machine:** MoonShots' GDN-layer skeleton, 1 dispatch with 9 grid barriers vs the eager 14-op chain: 0.419 vs 0.433 ms per layer (+3 %), both at ~165 GB/s against a 0.251 floor; lithos: with ~30 us of work per phase, in-kernel 81.7-84.7 vs 81.5 us per op with one dispatch per op; a persistent FFN -> GDN-in pair on an M5 Max 2.7 % slower [K]. TRIED: Megakernel / persistent kernel KILL; intra-layer megakernel BETWEEN (+3 %); M6b / R3 / #10 PARKED; the CPU-in-the-loop variant KILL.

## 7. TRIED and TABLE_350: why each design differs from what was tried
