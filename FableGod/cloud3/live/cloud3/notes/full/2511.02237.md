## 2. Mechanism (simplified Algorithm 1, l.60-104; general Algorithm 2, l.296-324)
- Acts on the router output of every MoE layer, per decode step, over the tokens of one decode batch; used "only during decode, not prefill" (l.521-524); implemented inside SGLang (l.512). No retraining; the single hyperparameter is k0.
- Phase 1 (per token, batch-independent): S_i^base = the token's top-k0 experts by router score, k0 < k. The general form caps this by a cumulative-mass top-p (n_i = min(k0, t_i), l.274-283), but p = 1 is adopted (l.436-439).
- Phase 2 (piggybacking): S^base = union of all S_i^base (l.89). For each token, walk its ranked list from rank k0+1 to N and add an expert iff it is already in S^base; the loop breaks when the test `|Si| > k` fires (Alg. 1 l.93-100). General form: cap k_max (adopted k_max = k = 8, l.405-411) and rank cutoff maxP (dropped, i.e. maxP = N, l.413-430).
- Unique experts loaded, T = |S^base|, is fixed by Phase 1; Phase 2 "maintaining the number of activated experts T = |S base|" (l.342-343).
- Weights: "we keep the model's original router scores and renormalize them following Equation (1)" (l.352-354); sum to 1. Re-scoring/weight adaptation "left ... to future work" (l.296-297).
- Latency model: per-expert cost f(n) = an + b; block latency = b·T + a·Bk (Eq. 2, l.142-156); memory-bound ⇒ latency ≈ linear in T.
- Calibration: none beyond choosing k0 via a cross-entropy sweep on 1M FineWeb-Edu tokens (grid in §3).

## 3. Setup
- Models (no shared experts): Qwen3-30B-A3B — 48 layers, N = 128 experts, k = 8, d = 2048, expert hidden 768, SwiGLU, bf16 (l.302-313); Qwen3-235B-A22B — 96 layers, d = 4096, expert hidden 1536, "same ... top-8/128 routing" (l.484-488).
- Hardware: 30B on one NVIDIA H100 80GB (l.302-305); 235B tensor-parallel on 8 H100 in one HGX node, NVSwitch, 18 NVLink per GPU pair (l.489-491). SGLang; CUDA graphs captured up to batch 16 so no padding tokens (l.628-629).
- Batch sizes: benchmarks with SGLang `--max-running-requests` = 16, i.e. "a batch size bounded at 16"; batch varies during serving (l.461-466, l.516-521); 32 not possible (KV cache). Cross-entropy sweeps: B ∈ {8, 16, 32, 64} (l.394).
- Benchmarks: AIME 24, MATH 500, GPQA, LiveCodeBench; temperature 0.6, top-p 0.95, up to 32768 tokens; 4 runs (30B) / 3 runs (235B), AIME 24 four times more runs (l.494-511).
- Cross-entropy: FineWeb-Edu subset, 2048 sequences of ≥ 8192 tokens (l.339-346); sweep uses 128 sequences × 8192 tokens at B = 8, halving length and doubling sequence count per batch doubling, 1M tokens total (l.394-399).
- Sweep grid: k0 ∈ {4,5,6,7,8}, k_max ∈ {7,8,9,10,11}, p ∈ {0.4,0.5,0.6,0.7,0.8,0.9,1}, maxP ∈ {8,16,32,128} (l.383-386). Benchmarks: simplified OEA with k0 ∈ {3,4,5,6,7} (30B) and {3,4,5,6} (235B, k0 = 7 skipped for cost, l.449-451), plus "pruned" (Phase 1 only) at the same k0.

## 4. Main results (benchmarks: batch capped at 16; normalised values as printed)
- Table 3 (30B, avg MoE-layer latency in µs over the 4 benchmarks): vanilla 175.7; OEA k0=3 106.8 (0.61), k0=4 120.9 (0.69), k0=5 136.0 (0.77), k0=6 151.3 (0.86), k0=7 163.0 (0.93). Text: "latency reductions of 39% for k0 = 3 and 23% for k0 = 5" (l.531-532).
- Table 4 (30B, avg unique activated experts, aggregated over layers and decode steps): vanilla 48.8; k0=3 25.1 (0.51), k0=4 29.9 (0.61), k0=5 35.1 (0.72), k0=6 40.3 (0.83), k0=7 44.4 (0.91); "k0 = 3 halving the number of activated experts" (l.530).
- Table 5 (235B, µs, "including all-reduce", TP = 8): vanilla 119.4; k0=3 87.7 (0.73), k0=4 94.8 (0.79), k0=5 101.4 (0.85), k0=6 106.9 (0.90). "a 15% speedup at k0 = 5"; the smaller gain is attributed to tensor-parallel all-reduce overhead (l.533-535).
- Table 10 (235B, unique experts): vanilla 54.0; k0=3 28.3 (0.53), k0=4 34.4 (0.64), k0=5 40.2 (0.74), k0=6 44.7 (0.83).
- Tables 1/6 (30B accuracy, OEA vs vanilla 80.4 / 60.2 / 62.1 / 92.8 for AIME 24 / GPQA / LCB / MATH 500): k0=3: 80.0 / 58.6 / 61.2 / 93.5; k0=5: 81.5 / 61.1 / 62.0 / 93.3; k0=7: 78.5 / 60.6 / 62.5 / 93.2. Pruned k0=3 (Table 7): 51.2 / 45.7 / 37.4 / 91.1 — piggybacking recovers nearly all of it at identical T.
- Tables 2/8 (235B, vanilla 85.0 / 68.4 / 68.5 / 94.7): OEA k0=5: 83.6 / 67.5 / 66.1 / 94.7; k0=3: 81.4 / 66.3 / 63.4 / 94.4. Pruned k0=5 (Table 9): 81.9 / 60.6 / 53.5 / 94.5 ("falling below the base model by 15% on LiveCodeBench, 8% on GPQA", l.484-485); pruned k0=3: 17.5 / 43.8 / 5.7 / 80.9.
- Fig. 1 (30B) and Fig. 4 (235B): mean MoE latency vs number of activated experts is linear, "R2 > 0.99" (l.511), standard errors "less than 2 · 10−4" (l.505). Derived from Tables 3-4 / 5-10: ≈ 2.9 µs per extra expert + ≈ 34 µs fixed (30B, one H100); ≈ 1.2 µs per expert + ≈ 53 µs fixed (235B, TP 8, incl. all-reduce).
- Fig. 2 (B = 16 cross-entropy Pareto): OEA dominates pruned at every expert budget (axes 40-57.5 experts, excess CE 0.01-0.07; no point values printed). Fig. 3/8: simplified OEA matches the best general setting. Fig. 5d: "negligible degradation at B = 64" (l.663-664). Fig. 6: maxP = 128 best, maxP = 8 "strictly worse" (l.768-769). Fig. 7: k_max ∈ {8, 9} best, 10/11 degrade (l.409-411). Fig. 9: p = 1 as good as p < 1.

## 5. Limitations and failure cases stated by the authors
- Gains depend on batch composition: similar tokens overlap experts, shrinking S^base; the benchmarks are that regime, so the reported numbers are "a conservative estimate" (l.632-641).
- Batch 1: "a batch size of 1 deems the piggybacking redundant" (l.346-347); no B = 1 experiment (with one token S^base = S_1^base, so only Phase-1 pruning remains, which alone drops AIME 24 from 80.4 to 51.2 at k0 = 3, Table 7). Batch-size-dependent k0 ("a bigger (safer) k0 at a lower batch size") left as an open problem (l.663-670).
- Assumes experts are not executed in parallel; expert parallelism only sketched (l.673-680). 235B gain limited by TP all-reduce (l.533-535). Latency model ignores kernel launch, padding, grouped GEMM (l.183-191).
- SGLang CUDA-graph padding tokens activated extra "out-of-distribution" experts, making batch 7 slower than batch 8; fixed by capturing graphs up to 16, padding mask recommended (l.614-631, l.644-646).
- Active-expert count "varies significantly across layers"; per-layer hyperparameters not explored (l.683-688). Relies on routing robustness; adapting expert weights after rerouting is open (l.691-699).
- 235B OEA k0 = 5 "declines slightly by 2%" on LiveCodeBench (l.486-488). Pruned-only routing collapses at low k0 (Tables 7/9).
- Fine-grained MoEs: both test models are N = 128 / top-8; authors argue the additive scheme suits "models with a high number of activated experts (k > 2)" (l.621-625). Shared-expert models (DeepSeek-V3, Kimi K2) only discussed, not evaluated (l.529-539). Speculative decoding: not stated anywhere.

## 6. Specific questions
- (a) Piggybacked expert weight = the model's own router score, renormalised over the kept set; not re-scored. "we keep the model's original router scores and renormalize them following Equation (1)" (l.352-354). "Other choices like using the weights of top-k are possible, but we leave such optimization to future work" (l.296-297).
- (b) k0: "We tested all values of k0 ∈ {3, 4, 5, 6, 7} on Qwen3-30B, and all except k0 = 7 on Qwen3-235B" (l.449-451); headline settings k0 = 3 (30B) and k0 = 5 (235B). Cap: k_max = k = 8 — "bounding the number of experts per token at exactly k works better than both smaller and larger choices" (l.406-408); sweep range k_max ∈ {7..11} (l.385).
- (c) Batch sizes: benchmarks "a batch size bounded at 16" (l.466); cross-entropy "B ∈ {8, 16, 32, 64}" (l.394). Batch 1 is discussed only qualitatively: "a batch size of 1 deems the piggybacking redundant" (l.346-347); B = 16 activates "up to 10×" the experts of B = 1 (l.198-200). No single-request measurement.
- (d) Unique experts per layer (avg over layers and steps): 30B 48.8 → 25.1 / 29.9 / 35.1 / 40.3 / 44.4 for k0 = 3..7 (normalised 0.51 / 0.61 / 0.72 / 0.83 / 0.91, Table 4 l.602-611); 235B 54.0 → 28.3 / 34.4 / 40.2 / 44.7 for k0 = 3..6 (0.53 / 0.64 / 0.74 / 0.83, Table 10 l.866-875). Note: vanilla 48.8 is far below the paper's uniform-routing expectation of 82 at B = 16 (l.196); batch size varies during serving.
- (e) Speculative decoding: not stated. Consecutive tokens of one sequence in a batch: no. In the cross-entropy simulation each batch is the t-th token of different sequences and "No information (experts or scores) is shared across different positions, so piggybacking never crosses decode steps" (l.354-356); benchmarks use ordinary one-token-per-sequence decode.
- (f) No hypothesis test; a per-cell standard-error rule: "A result µ ± se is considered standard-error adjusted worse than µvanilla ± sevanilla when µ + se < µvanilla − sevanilla" (l.523-524); se over 4 (30B) / 3 (235B) runs, passing cells bold in Tables 1-2 (bold is not visible in the text dump). Applying the rule to Tables 6/8: every 30B OEA cell passes (k0 = 3 GPQA: 58.6 + 1.22 = 59.82 > 60.2 − 0.83 = 59.37); 235B k0 = 5 fails on LiveCodeBench (66.1 + 0.63 = 66.73 < 68.5 − 0.21 = 68.29), conceded in the text as a 2% decline.

## 7. Verification of secondary-source claims
- "39% and 15% MoE-layer decode latency reduction for Qwen3-30B-A3B and Qwen3-235B at batch 16": CONFIRMED (abstract l.24-26; Tables 3/5 normalised 0.61 and 0.85; l.531-534). Caveats: 39% is at k0 = 3 and 15% at k0 = 5; "batch 16" is a cap (`--max-running-requests`, batch varies, l.461-466); the 235B figure includes TP all-reduce (Table 5, l.650); MoE-layer latency only, not end-to-end.
- "no statistically significant accuracy loss": CONFIRMED as the authors' claim (l.24-25, l.644-645) under their standard-error rule (l.523-524); it holds for 30B at every k0, but for 235B at k0 = 5 the authors themselves report LiveCodeBench 68.5 → 66.1 (l.486-488), which fails their own rule.
- "OEA is additive (baseline + already-active experts) whereas Lynx is subtractive": CONFIRMED. Lynx: "subtractive approach: first the union of experts that would normally be activated is computed; then, the least popular among these experts are dropped" (l.584-586, l.614); "OEA is an additive and opportunistic framework" (l.616).
