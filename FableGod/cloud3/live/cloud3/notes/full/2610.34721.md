## 2. Mechanism (Sec. 4 / Algorithm 1, l.206–269; Sec. 4.2 l.274–300)
- Logical cache: per layer l a residency set R_l (|R_l| <= C), an eviction priority and its statistics; a deterministic function of the token history and policy parameters only. Reset per sequence to a fixed warm set (the C most frequently selected experts of that layer on held-out text). Physical copies change latency, never outputs; harness and engine run the same logical cache (Table 1: ppl 8.509 constant vs physical-cache routing 8.755 -> 8.627 as in-flight prefetches go 1 -> 4).
- Build, part 1 at layer l-1 ("bounded prefetch steering"): pre-gate ranking g = layer l's router applied to layer l-1's MoE input (ready ~0.4 ms ahead; one expert copy 0.55 ms). Visit g[1:8] in rank order (window 8 on OLMoE; 4 on Moonlight; 4 or 2 of 16 on Qwen3.6). Visited resident candidates are protected; at most n (1 or 2) non-resident candidates are inserted into R_l (evicting the lowest-priority unprotected expert if |R_l| = C) and a prefetch copy is queued. "Unbounded" (n=8) inserts every non-resident candidate.
- Routing, part 2 at layer l: S <- TopK(z + lambda*Dbar_l*1[e in R_l]) — Cache-Prior's logit bonus (Eq. 1) applied to the logical set; ties toward the router's own ranking, then lowest index. No reroute, no substitution, no expert dropped: all K router-selected experts execute; every e in S \ R_l is inserted (evicting the lowest-priority expert outside S u B) with an immediate demand copy. Weights: "execute S with weights softmax(z)_S" (l.239), i.e. the unmodified softmax; renormalisation over S: not stated. "the router still makes the final choice among resident and non-resident experts" (l.1417–1419).
- Eviction ("A priority", l.259–269): p_e = sbar_fast_e + sbar_slow_e + pi_l(x_t)_e — EMAs (decay 0.5 and 0.98) of the indicator that the router's OWN top-K contains e (so the bias does not reinforce itself), plus token prior pi_l(x) = frequency with which layer l routes input token x to each expert on held-out text. Computed once per step, before insertions.
- Physical/prefetch side (4.2): engine mirrors Alg. 1 and issues one copy per logical insertion; demand copies immediately; prefetch copies queued at layer boundaries with at most two in flight; one ordered copy stream with per-slot events; a layer waits only on the slots it executes; a queued prefetch whose slot was reassigned is dropped. Warm-set copies happen in prompt processing. Host policy ~20 us/layer (numba + numpy), ~0.3 ms/token.
- Training: none (training-free). Calibration on held-out text only: token prior, warm set, Dbar_l (average logit range). lambda, n and the window were picked on the selfgen KL diagnostic plus engine latency. Distillation-trained gates and post-trained PSR (Sec. 6.10, LoRA rank 16/8, 4.5M / 3.9M tokens) cut selfgen excess 17–30% / ~20% but did not improve benchmarks.

## 3. Speculative decoding with block-level expert selection (Sec. 7, l.1195–1384; App. B l.1751–1763)
- This is AcceptMoE's (Liang et al., 2026) block-level selection plus the authors' variant, run as an SD baseline AGAINST PSR; it is not part of PSR. The AR-PSR rows of Table 9 use the ordinary per-token logical cache (C = 24, n = 1).
- Granularity: "restricts verification to one eligible expert set per block and layer ... every position then routes within the set" (l.1206–1211). Set per layer and block (l.1751–1755): A = root position's own top-K, plus the min(ceil(gamma*e^H), m) experts outside A with highest weighted demand u_e = sum_d alpha_d * r_{d,e} * 1[e in TopK(z_d)] (r_d = router softmax at draft depth d; m = number of experts outside A with u_e > 0; H = -sum_{e not in A} q_e ln q_e, q_e = u_e / sum_{e' not in A} u_e'). Non-resident members are then "pruned in increasing order of demand within AcceptMoE's rerouting budget" (budget itself: not defined here). gamma scales the set size, not the weights.
- Drafter confidence (l.1243–1246): "we weight each position's demand by the drafter's cumulative confidence in the draft up to that position, alpha_d = (prod_{i<=d} c_i)^{1/2}, where c_i is the drafter's probability of its own token" — square root of the running product. App. B l.1759–1762: AcceptMoE position weights "alpha_d = p_d^{1/2} with p_d the measured commitment rate at depth d and gamma = 1"; "confidence weights alpha_d = (prod_{i<=d} c_i)^{1/2} with gamma = 1.05; alpha_0 = 1".
- Positions/experts outside the set: a position routes within the set (restricted selection; the exact within-set rule and weight handling are not stated beyond "routes within the set"), except the top-1 rescue (l.1250–1254): each position with alpha_d >= 0.3 keeps its own top-1 expert even if it lies outside the set. Without the rescue, displaced top-1 experts give KL about twice PSR's at the same displaced router mass.
- Pool: P = 24 experts/layer on OLMoE (64 on Qwen3.6) between blocks, LRU, refilled by recency after each block; Qwen adds 64 slots for a block's union. k = 16 drafts from OLMo-1B-0724 (greedy; k = 8 timed only); k = 15 from DFlash on Qwen3.6. The set is chosen from the layer's own router outputs after its attention, with no prefetch, so each verification copy is exposed (0.57–0.60 ms vs PSR's effective 0.31–0.32 ms).
- Determinism: the pool is a function of token history + drafts (reproducible), but output depends on the drafter and k: in a replay of 3346 blocks, 36% of committed token-layers execute a different expert set when rejected positions carry the drafter's wrong tokens (l.1365–1373). A per-position logical cache with rollback would reproduce PSR's output but in CPU replay needed 1.4–4x the copies, and at k = 16 more than PSR itself.

## 4. Setup
- OLMoE-1B-7B-0924-Instruct: 16 MoE layers x 64 experts, top-8; expert 12.6 MB bf16, 12.9 GB total; C = 32 (50%), 16 (25%), 24 (37.5%, Sec. 6.10 and 7). Model fits the GPU, so memory pressure is emulated by capping the cache.
- Moonlight-16B-A3B-Instruct (DeepSeek-V3 arch): 26 MoE layers x 64 routed experts, top-6 sigmoid router with bias, 2 shared experts; expert 17.3 MB; 31 GB (real offload); C = 32/24/16; benchmarks at C = 24.
- Qwen3.6-35B-A3B FP8: 40 layers (30 Gated DeltaNet + 10 gated attention), 256 routed experts, top-8 softmax, 1 gated shared expert; expert 3.2 MB, copy ~0.14 ms; routed experts 33 GB (model 37 GB); C = 128/96/64; benchmarks at C = 64; SD pool 64 + 64 slots; AR up to C = 148.
- Hardware: one NVIDIA RTX 4090 (24 GB), PCIe 4.0 x16, 22.9 GB/s measured, 0.55 ms per OLMoE expert copy, process pinned to 16 CPU cores; all-resident OLMoE decodes at 6.8 ms/token. Engine: PyTorch, two CUDA graphs per layer, vLLM fused MoE kernel, FlashAttention-2, experts in pinned host memory, static KV cache.
- Batch sizes: engine batch 1 throughout; harness batch 1 for OLMoE; Moonlight and Qwen3.6 harness in batches of 8 on two GPUs (MBPP 4; Qwen likelihood tasks 2), one logical cache per row.
- Benchmarks (lm-evaluation-harness 0.4.13, greedy): MMLU 0-shot (14,042 q), ARC-C, HellaSwag (0-shot acc), GSM8K 5-shot strict, BBH 3-shot CoT (100 q x 27 subtasks), IFEval strict prompt/instruction, HumanEval, MBPP (pass@1). Latency: 12 teacher-forced windows <= 1024 tokens (WikiText, C4, self-sampled; ~9.8k tokens), mean of 3 rounds, paired t-test on log latency; selfgen KL diagnostic on 44 windows (132 on Moonlight, every second one on Qwen).

## 6. Limitations and failure cases (Sec. 9 l.1496–1512 and text)
- Three models, one GPU; OLMoE memory pressure emulated. "OLMoE and Moonlight have 64 fine-grained experts per layer, Qwen3.6 has 256; models with fewer, larger experts (e.g. Mixtral) leave less room for cache-aware routing." Findings transferred to Moonlight only after retuning the pre-gate window (depends on how close the link is to saturation); on Qwen3.6 (256 experts, top-8, 3.2 MB experts) copies are cheap vs compute, PSR's latency advantage over Cache-Prior disappears and only its lower KL and likelihood-task gains remain. "The numbers need to be re-measured for other models and links."
- The whole study is single-request batch-1 decode; the batched high-throughput regime (MoE-Lightning) is called "a different regime"; no throughput results. Moonlight/Qwen harness benchmarks were decoded in batches of 8 (Qwen: six tasks, changed GSM8K protocol).
- No external systems (llama.cpp, MoE-Infinity, CPU execution of experts, named as "a competitive alternative that PSR could be combined with"); SMoE-style substitution not implemented; operating points not pre-registered.
- Main latencies are teacher-forced and exclude prompt processing; in greedy generation the PSR-over-CP gap shrinks and reverses on HumanEval at 50% ("short, repetitive outputs leave little for prefetching to win"). Host-side selection ~0.3 ms/token (4.6 ms uncompiled on Qwen). Generative paired SEs 0.8–3 points; harness–engine agreement only statistical (21% of GSM8K answers differ under exact routing; resolution ±3.2–4.8 points).
- At 25% residency every cache-aware configuration loses on BBH (PSR −2.6, p = 0.002; CP0.2 −2.3): "no method is free on multi-step reasoning". Unbounded insertion (n=8) is closest to exact but at 17.0 ms is slower than CP. Gate training improves the KL diagnostic but not benchmarks (HellaSwag −0.8 sig for post-trained PSR).
- SD: greedy, one drafter per target; OLMoE conclusion (needs a much cheaper drafter) rests on measured components; Qwen block-selection quality rests on 64 prompts and its latency on these kernels and prompts; block selection's output depends on the drafter and k.

## 7. Verification of project-note claims
- "PSR section 7 weights each verify-block position's expert demand by the square root of the running product of drafter confidences, with gamma 1.05, builds one expert set per block and reroutes inside it": CONFIRMED on formula and numbers — alpha_d = (prod_{i<=d} c_i)^{1/2}, alpha_0 = 1, gamma = 1.05 (l.1243–1246, 1762) — with three precisions: (a) one set per block AND per layer (l.1206–1207, 1751); (b) positions reroute within the set except the top-1 rescue: any position with alpha_d >= 0.3 keeps its own top-1 expert even outside the set (l.1250–1254); (c) it is the authors' variant of AcceptMoE's block-level selection, an SD baseline measured against PSR in Section 7, not PSR's own routing, and gamma sizes the set (ceil(gamma*e^H)) rather than entering the weights.
- "PSR decides against a deterministic logical residency set and reroutes within it on every token": WRONG. PSR's defining choice is FOR a deterministic logical residency set R_l per layer (l.98–100, 242–247; Table 1), and it does not reroute within it: selection is TopK(z + lambda*Dbar_l*1[e in R_l]) (Alg. 1 line 15), so non-resident experts are selected whenever the bonus does not outweigh their margin, triggering demand copies (Alg. 1 lines 16–18; 2.2 demand copies/token at the 10.7 ms point, 16.4 at 25%); "the router still makes the final choice among resident and non-resident experts" (l.1417–1419). What PSR decides against is routing on the physical, timing-dependent cache (Sec. 3) and substitution of missed experts (not implemented, l.1442–1443).
