# Cascade: Utility-Driven Speculative Decoding for Mixture-of-Experts (arXiv 2506.20675)

**Authors / affiliations / date.** Anish Saxena, Hritvik Taneja, Moinuddin Qureshi (Georgia Tech); Po-An Tsai, Aamer Jaleel (NVIDIA Research). arXiv:2506.20675v1 [cs.DC], 17 Jun 2025 (L1-12). Source: /root/c3dl/txt/2506.20675.txt (pdftotext -layout, 1554 lines; "L" = line there).

## 1. Mechanism
- Speculation utility (Def. 4.1, Eq. 2-3, L674-685): cost = t_iter,spec / t_iter,base; benefit = ETR_spec (tokens the target emits per iteration); **U_spec = ETR_spec / (t_iter,spec / t_iter,base)**. Cost = full iteration time incl. drafting + verification + rejection sampling, normalised to the no-spec iteration (L711-714).
- Theorem 4.2 (L721-723): TPOT_spec = TPOT_base / U_spec, so maximising U minimises TPOT. Fig. 8: over 120 points (5 MoEs x 3 tasks x K in [0,7], n-gram) utility predicts speedup with "R^2 = 99.4%" (L703-710).
- Test-and-set (Fig. 10, L774-789): per request, test phase = up to M=4 trials of t=4 iterations (T = M*t = 16), then set phase S=16 iterations at the best-utility K; "test-and-set interval is short (32 iterations)" (L90). First trial uses K_start = the non-zero K with the highest recent utility (L782-785); initial default "static K=3 configuration (our chosen k_start)" (L1283). Baseline t_iter,base: first ~4 decode iterations run without speculation, refreshed "infrequently (e.g., every 100 iterations)" (L786-789).
- Turning speculation off (§5.4, L791-802): at the end of each trial, utility < 1 -> K=0 for the next set phase; "If the current K is already 1, we exit the test phase early"; K=1 is the most conservative speculative state because acceptance is causal. Testing restarts every t+S iterations "beginning each cycle with K=1", so speculation can be re-enabled.
- Adaptive back-off (§5.5, L843-855): "double the set phase length S whenever K drops to 0" (exponential back-off of test frequency). Example: over 250 iterations only 18 speculative trial iterations vs ~50 without. Cuts worst-case slowdown (Mixtral+math) "from 14% to just 5%" (L103, L853-855).
- Hill-climbing K search (§5.6, L826-840, L857-871): compare utility at prev-K vs curr-K; if utility rose with higher K keep raising K, otherwise backtrack; keep best-K for the set phase. Early exit when (1) utility falls over successive trials, (2) K reaches 0, or (3) successive utilities "converge within 10%". Only hyperparameters: t=4, T=16, S=16 (L1148-1158). Cascade's K ceiling: not stated (Fig. 12 axis shows test-k 0..4, L819); static baselines capped at K=3 (L641-643).

## 2. Setup
- vLLM v0.6.6, ~500 LoC Python/PyTorch (L862-863); EAGLE runs ported to vLLM v0.8.2 (L1389). Drafter executed even when speculation is off (KV consistency for model-based drafters), "2–3% on average" overhead (L1127-1134). MoE iteration time 6 ms (OLMoE) to 28 ms (Mixtral) (L1139).
- Table 1 (L588-606) hidden/layers, active/total params, experts, top-k, shared: Mixtral FP8 4K/32, 13B/47B, 8, top-2, 0; Phi-3.5 FP8 4K/32, 6.6B/42B, 16, top-2, 0; OLMoE FP8 2K/16, 1B/7B, 64, top-8, 0; DeepSeekV1 FP16 2K/28, 2.8B/16.4B, 66, top-6, 2 shared; Qwen-1.5 FP16 2K/24, 2.7B/14B, 64, top-4, 4 shared.
- Batch size: **single-batch only** ("single-batch serving, which is the focus of this work", L22-23; "our single-batch serving setup", L653). No other batch size is run.
- Hardware: one RTX 6000 Ada 48 GB + Intel i9-14900K (24-core/32-thread), 64 GB RAM (L644-646). Dense reference: LLaMA-3-8B.
- Workloads (L613-633): math = GSM8K, code = HumanEval, extraction = MT-Bench "extraction"; four mixed streams of 2-3 tasks with equal shares (code+math 50/50, All-3 33% each), 10-minute runs, >= 20,000 tokens; 7 tasks total. Drafters: n-gram (prompt lookup) on all five MoEs, EAGLE on Mixtral only. Static baselines K in {1,2,3} ("maximum K of 3 ... increasing K further yields, at-best, marginal benefits", L641-643); motivation figures sweep K to 7. Metric: output tok/s = 1/TPOT, plus ETR and overheads (L651-654).

## 3. Headline numbers (all batch 1, n-gram unless noted)
- Dense LLaMA-3-8B (Fig. 4, L189-202): ETR 1.5x-2x, TPOT 1.4x-1.8x at K=7; total spec overhead 5-10%, verification "maximum of 3%".
- Mixtral 8x7B (Fig. 4, L306-326): ETR 1.6x-3.2x at K=7, but code 3.2x ETR -> only 1.4x TPOT; math and extraction slower at every K; **verification overhead at K=7: 3x math, 2.3x code, 2.6x extraction**; caption: overheads "1.5x-3x", TPOT slowdown "upto 2x"; drafting + rejection sampling only 1-2%.
- Expert activation (§2.4, L333-345): attention = 8% of baseline latency, flat in K; at K=7 Mixtral verifies 8 tokens x top-2 -> "over seven unique expert activations, on average, a 3.5x increase in data movement, based on a bucket-and-balls analysis" (uniform-router assumption); real overhead lower via affinity, "only a 3x overhead at K=7" on math. Intro example: 3 draft tokens -> "up to 6 experts" of 8, "3x increase in data movement" (L46-47).
- Static-K across models (Fig. 5, L320-331, L344): Mixtral K=3 +39% code / -54% math, 50/50 math+code mix +13%; Mixtral K=1 math -25%; Phi K=1 math -10%, Phi extraction up to +20% at K=3, Phi math+extraction no gain at any K. Fig. 7 (L660): OLMoE extr K=3 +70%, Phi extr K=3 +23%, Mixtral math K=3 -54%. 18 of 35 model-task pairs degrade, up to 1.5x (L1442-1444).
- Cascade vs static (Fig. 13, §7, L1106-1139): static worst-case slowdown 26% / 38% / 54% at K=1/2/3; Cascade worst-case 5%; gains on all MoEs, DeepSeek only +1%; OLMoE static K=2/K=3 +31%/+33% vs Cascade +29% (caption: "3% average slowdown compared to static K=3", test-phase cost); Mixtral +18% over best static K=2, Mixtral code +57% vs +39% static K=3. Caption: "7-15%" over static-K, "up-to 1.6x" vs no-spec; abstract/intro/conclusion: 7-14% (L45, L133, L1450); "up to 14% average performance gain for Mixtral" (L116); 20% average vs no-spec when speculation helps (L119-121).
- Per-request (§7.1, L1148-1157): static-K shows within-request instances of up to 2x slowdown; Cascade's max per-window loss 33%, in only 3 instances (test phases).
- Ablation (Fig. 18, L1276-1291): static K=3 -> +disable -> +back-off -> +hill-climb, "additive" (no numbers in text). Sensitivity (§7.5, L1377-1389): t=2 -> 13% avg gain, S=32 -> 4%, t=4/S=16 -> 20%.
- EAGLE on Mixtral (§7.3, L1376-1388): ETR 1.7 vs 1.3 (n-gram) on math at K=1; drafting cost grows "5% per unit increase in K", so static K=1 is best; Cascade gives "only modest gains over static K=1" but matches the best static K on all tasks.

## 4. Limitations
- Batch size 1 only, no batch sweep and no claim about larger batches (L22-23, L653). One 48 GB GPU; largest model Mixtral 47B (FP8); no multi-GPU or DeepSeek-V3-class MoE.
- Unique experts per verification step are never measured; the only expert-count figure is the analytic bucket-and-balls estimate for Mixtral at K=7 (L336-340). Cost is tracked only as an iteration-time ratio.
- The 2.3x-3x verification ratios are quoted at K=7, beyond the K<=3 the system actually runs; overhead at K<=3 is not tabulated. Bar values of Fig. 5/13/18 are not in the text.
- Mainly n-gram drafting; EAGLE on Mixtral only, with modest gains. Cascade needs no-spec baseline iterations (first ~4, refreshed ~every 100) and pays test-phase cost (OLMoE -3% vs best static, per-window losses up to 33%).

## 5. Answers
(a) Unique experts per verification step vs K, per model: **not measured for any model.** Only statement, Mixtral K=7: "eight tokens per step and selects two experts per token. Assuming uniform random selection of experts by the router, this leads to over seven unique expert activations, on average, a 3.5x increase in data movement, based on a bucket-and-balls analysis. In practice, the increase is lower due to expert affinity" (L336-342); "the math task in Fig. 4 shows only a 3x overhead at K=7" (L343-344); measured K=7 verification overhead 3x math / 2.3x code / 2.6x extraction (L326). Other models qualitative only: OLMoE has "strong expert-to-token affinity [36], which lowers verification cost" (L1127-1128); Mixtral "exhibits low expert-to-token affinity" (L1129-1130). Phi, DeepSeek, Qwen: not stated.
(b) Batch 1 is the whole paper, and speculation does lose, even at K=1: Mixtral "two tasks–math and extraction–suffer slowdowns for all speculation lengths" (L316-317); "every workload experiences slowdown for at least one K, and three (math, extract, math+extract) suffer slowdown across all K-values" (L55-56, Mixtral K in {1,2,3}); "Mixtral incurs a 25% slowdown on the math task" at K=1 (L344) and "a 54% slowdown on math" at K=3 (L322-323); Phi "incurs 10% slowdown on math at K=1" (L327-328); static "worst-case slowdowns of up to 26%, 38%, and 54% for K = 1, 2, and 3" (L1118-1119).
(c) Optimal K vs batch size: **not stated**; only batch 1 is run. The sole batch remark is about prior SLO work "designed for non-latency critical scenario of batch sizes that make decoding closer to compute intensive 'knee' of the GPU" (L1395-1397). Within batch 1, optimal K "depends on the task, model architecture, and varies even between requests and iterations" (L103-105).

## 6. Verification
- "draft tokens activate 2-3x more weights, verification time 2-3x": **CONFIRMED as the paper's claim** ("draft tokens collectively activate more weights, increasing data movement and verification time by 2–3x", L25-27; Fig. 1 "2x-3x", L85-86; conclusion L1439-1440). Measured support is verification-time ratio on Mixtral at K=7 (3x/2.3x/2.6x, L326; Fig. 4 caption "1.5x-3x", L306); the weight/expert count is analytic (3.5x uniform estimate at K=7, L339), not measured.
- "slowdown capped at 5 %": **CONFIRMED** — "Cascade limits worst-case slowdown to just 5%" (L1119-1121; also L44, L130, L853-854, L1449), worst case = Mixtral+math, average over a run. Caveat: per-16-iteration windows show losses up to 33% in 3 instances (L1156).
- "+7-14 % over static K": **CONFIRMED** in abstract/intro/conclusion (L45, L133, L1450); Fig. 13 caption says "7-15%" (L1108). Mixtral specifics: "up to 14% average" (L116) vs "18% over the best-performing static K=2" (L1133) — the two Mixtral numbers are not reconciled in the text.
