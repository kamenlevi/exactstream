## 0. Verdict in seven lines
1. **The wall is one equation:** bytes per token = (trunk per pass + expert union per pass) ÷ tokens kept per pass. The trunk is 2.7 GB with HC8 (3.3 today) and cannot go lower for this model (3-bit dense +12.5 % ppl, HC4 6 % flips [K]). The union grows ×1.5-1.6 per doubling of the pass width [K, routing capture], and kept per pass is capped by the drafter: today's keeps 10.5 at 16 rows and 10.5 at 32 (DS, DS2: the depth decay eats the width) [K]; a 0.96 chain without decay would keep 11.5 / 17.5 / 22.2 at 16 / 32 / 64 [P]. So wider passes do not cut expert bytes per kept token (×1.5 worse at 32 rows with today's drafter, flat at a 0.96); they only amortise the fixed time, and a ≤ 0.96 is where every buildable drafter stops (sub-1B drafters 0.93, +8-20 % kept paid, the near-copy 0.983 is the trunk itself [K D-01]).
2. **The true ceiling of this Mac on code with no design assumptions** [P]: a perfect drafter and the oracle gate at 32-64 rows would need 0.17-0.25 GB per token (1,100-1,650 tok/s at 284 GB/s); with the measured drafter ceiling (a 0.96) the oracle gate gives 0.46 GB (620) and the realizable gate 0.60 GB (470); compute, launches and the night SSD all sit above those. **1,000 tok/s on code therefore needs kept ≥ 25-30 per pass, i.e. a drafter at ≥ 0.98 over 32-64 positions, and the only such drafter is the 125B's own trunk, which costs a trunk pass per draft (D-07). That is the physical limit, and it is a knowledge limit, not a bandwidth limit.**
3. **The realizable design lands at ~350-470 on code at the byte floor and ~280-350 with real kernels** [P/G]: the 32-row banded pass (NAX32 at 1.7-1.9 ms per added row today [K], the cf ≥ 0.999 gate at 0 flips [K], the runahead to hide the SSD, HC8, the fused dense body at 15-18 ms [K C0], the 6.3 ms 4-bit drafter [K D7b], DFlash3 + HPD at ~0.955). Exact mode on the same engine ~180-220. Chat's ceiling is the drafter (kept 2.6 with the chain): ~100-150 with the trunk-as-drafter (D2), ~90 without.
4. **Where the time goes once the experts are cut** [K C0]: the dense trunk runs at 30-36 ms per pass against a 9.5-11.6 ms byte floor (GDN 12.4 ms = 2.3× its bytes, HC reads 11.4 = 5×, attention 7.5 = 4-5×, router / shared / tail 5, head 2.5), because 48 layers × ~60 kernels at M = 16 never saturate the memory system; Leap's C0 puts the reachable constant at 15-18 ms. The expert kernel streams at 146-172 GB/s against 284 (1.5-1.7× headroom, C2 PASS). These two, not bytes, set the realizable number.
5. **Three design-level levers survive the physics**, each with a one-night test (section 4): the 32-row runahead pass (fixed time + SSD; +20-38 % modelled at 32 rows, M-16); draft-ahead from the predicted cut points in SSD-idle time (exact; 70 % of code checks end at the block end or one of the two lowest-confidence positions [K, new]; the SSD is busy 102 ms per check against a 12 ms draft at C 224); and the trunk-as-drafter for chat (D2, 2-bit trunk copy, chat ×2-3). Whole-layer skips cannot pay by sureness (drafter-sure runs are 1-2 tokens, so no 16-row pass is all-sure [K D1]); only an all-row skip of a redundant layer group would, and that is a one-night map test with an unlikely prior.
6. **The one design to bet on** (section 5): the 32-row banded pass with the k-head gate, runahead, HC8, the fused body and the 4-bit drafter, chat on D2. Expected code ~300 (45 GB, day) / ~350 (C 320 or runahead, night) quality-defined, ~200 exact; mixed workload ~150-170. It breaks 350 with margin on code and nothing breaks 0.3 GB per token.
7. **What would break 0.3 GB per token:** a drafter that carries the 125B's knowledge at its unsure positions for ≤ 0.1 GB per block, which no conversion of this model gives (every cheap drafter ≤ 0.96; a 2-bit trunk copy costs 0.9 GB per draft step and is sequential), or a model whose trunk is read once per 30+ tokens by construction (BLUEPRINT's chaining head trained into the model). On this model, on this Mac, the floor is ~0.46 GB (oracle gate, 0.96 drafter) and ~0.31 only with a perfect drafter at 16 rows.

## 3. The structure that every design must respect
- **The equation** [P on K]: per token, bytes = (T + U(B)) / kept(B), where T = 2.7-3.3 GB, U(B) is the union per pass and kept(B) is what the drafter's chain keeps at width B: measured 10.5 at 16 and at 32 rows for DFlash2 (DS, DS2: the per-depth rate falls 0.934 → 0.889 past 10 rows, so the width buys nothing); for a chain without decay kept(B, a) = (a − a^(B+1)) / (1 − a): a 0.945 gives today's 10.5 at 16 rows, a 0.96 gives 11.5 / 17.5 / 22.2 at 16 / 32 / 64.
- **U(B) measured on code** (wall_union_width.py; 45 GB tiers, 205 / 97 / 43 blocks):

| scheme | 16 rows | 32 | 64 | ratio 32 / 16, 64 / 16 | MB per kept, today's drafter (16 / 32 / 64) | a 0.96 chain |
|---|---|---|---|---|---|---|
| exact | 8,366 MB | 12,556 | 18,119 | 1.50, 2.17 | 797 / 1,196 / 1,726 | 727 / 717 / 816 |
| cf ≥ 0.999 top-2 | 5,967 | 9,360 | 14,063 | 1.57, 2.36 | 568 / 891 / 1,339 | 519 / 535 / 633 |
| NEW-1 bands | 4,894 | 7,777 | 11,850 | 1.59, 2.42 | 466 / 741 / 1,129 | 426 / 444 / 534 |
| 125B-sure oracle | 3,359 | 5,367 | 8,285 | 1.60, 2.47 | 320 / 511 / 789 | 292 / 307 / 373 |
| top-2 everywhere | 2,560 | 4,164 | 6,593 | 1.63, 2.58 | 244 / 397 / 628 | 223 / 238 / 297 |
Consequences: (i) with today's drafter a 32-row pass costs 1.5× the expert bytes per kept token and 2.2× at 64; with a 0.96 chain it is flat to 32 rows and worse at 64; (ii) the trunk per kept token falls 0.23 → 0.15 → 0.12 GB (B 16 → 32 → 64 at a 0.96), so B 32 is the optimum once the drafter holds ~0.96 without decay, and its gain is the amortised fixed time, ~10 % in bytes and ~25 % in time at the floor; (iii) only a ≥ 0.98 makes 64-row passes pay, and that drafter does not exist below the trunk; (iv) with today's drafter the 32-row pass pays only through the runahead's SSD hiding, not through bytes.
- **Sure runs** [K]: the 125B is sure on 86.8 % of code rows in runs of 13.7; the drafter at cf ≥ 0.999 on 47.7 % in runs of ~1 (D1). Any mechanism that needs a whole pass to be sure (skip a layer's weights for everyone) never fires on the realizable gate.
- **Cut points** [K, wall_cutpoints.py on D-23's logs]: code checks end at the block end 47 % of the time; of the breaks, 23 / 44 / 67 % fall at the lowest / two lowest / three lowest-confidence positions; so three candidates (the end and the two lowest) cover 70 % of code checks (chat 80, agent 59, math 56). Median SSD-busy time per check 102 ms (code, C 224) against a 12 ms draft.

## 4. Design-level ideas
### 4.1 The 32-row runahead pass on NAX32 with the banded gate
- **Mechanism.** The unit of work becomes a 32-row pass: rows 1-16 are the exact re-check of the previous runahead block (all experts present), rows 17-32 the next block computed with the cache's experts only (misses skipped, loads issued), re-checked next pass (M-16). Per-row k from the drafter's band through the sync-free gate; NAX32 for the expert phase; the commit of accepted rows per pass.
- **Bytes / compute / time** [P on K]. Trunk once per pass (2.7 GB); union at 32 rows 7.8 GB (bands) → at a 0.955 kept ~17 per pass: 0.62 GB per kept token; rows at NAX32's 1.7-1.9 ms today (1.0-1.2 with the gate's pairs ×0.48, 0.86 at the byte floor); dense +2.6 ms (D32); the SSD waits replaced by the runahead's misses-skipped rows (M-16 at 32 rows: +20-38 % modelled at β 2.5-4.0 [K model]; β measured 1.7-2.1 today [K]). Check ≈ 18 (fixed) + 2.6 + 32 × 1.1 + 6 (draft) + ~3 (SSD residual) = 65 ms per 17 kept = ~260 tok/s with today's kernel efficiency, ~350 at the byte floor.
- **Must be true.** kept(32) ≥ 14 with the next drafter (a ≥ 0.95: HPD / DFlash3); the runahead's re-check matches bitwise (M-16's harness has it); the 32-row dense at 1.24×; β ≤ 2.5 (PASS today).
- **Test, kill.** DS2's walk at block 32 with the HPD drafter: kept ≥ 14 (kill < 12.5: then B 32 pays only through the runahead's SSD hiding, +20-38 %); the live 32-row runahead A/B on the M-16 harness at C 256, 10 min once built (multi-day build MoonShots → Leap → BigMoE). Exact in its exact form; QD with the gate.
- **TRIED.** M-16 was KILL at 16 rows (per-row cost 2.64, the cap); the 32-row build was left open on β ≤ 2.5, which B3 measured today at 1.7-2.1: the reason is removed. K-62L (NAX live KILL) died SSD-bound at C 160; C 256 + the gate make the loop GPU-bound. Shadow cache (pays the fixed part twice) is not this: one pass, one trunk read.

### 4.2 Draft-ahead from the predicted cut points, in SSD-idle time (exact)
- **Mechanism.** While check i waits on the SSD (102 ms busy per code check at C 224 [K]; 11-25 ms at C 256 + M-17 at the floor), the GPU drafts block i+1 from three candidate prefixes: the block end and the two lowest-confidence positions of block i's draft. When check i ends at one of them (70 % of code checks, 80 % chat [K]), the next draft is ready; otherwise it is drafted serially as today.
- **Bytes / time** [P]. No extra bytes of weights beyond the drafter's (0.24 GB at 4-bit, resident); 3 × 6.3 ms of GPU inside SSD-idle time; saves the serial draft on 70 % of checks: −4.4 ms per check on code today (−8.8 at 12.5 ms), i.e. +5-7 % today and +7-10 % on the realizable floor engine by day (where the draft is 6 of 60 ms and the SSD exposes ≥ 6 ms); 0 at night with the SSD hidden.
- **Must be true.** The candidate prefixes' hidden taps are available before the check ends: the two lowest-cf cut points need the trunk's hidden states at those rows, which the check produces layer by layer, so the draft starts after the check's last layer but before its SSD-bound expert loads complete — the OOO order must expose those rows' final states early (it computes resident rows first). The drafter's 5 taps for a cut point inside the block are the check's own states at that row (exact, since prior rows are drafted-then-verified). If the taps are only available at check end, the gain is the overlap with the commit and the next check's first layers only (~2 ms).
- **Test, kill.** Replay first (CPU, done above: 70 %); then a 10-min live A/B at C 224-256: cycle time −4 ms or more on code (kill < −2 ms, or any token differing from REF2-T).
- **TRIED.** "Pipelined pre-drafting from every cut point" was priced out (8-10 ms of GPU for ~8 ms saved): the reason was GPU cost on the critical path; here only three candidates run, in time the GPU idles anyway, with a 6.3 ms drafter. R-70D (prefetch in the draft window) and Rnd23 (prefetch from the MTP state, recall 0.09-0.24) are the SSD side, not this.

### 4.3 Whole-layer skips (QD): only all-row skips of a redundant group can pay
- **Why the stated form is empty** [P on K]: the trunk's weights are read once per pass whatever the rows do; skipping layers on sure rows saves only their share of the dense ALU, which is flat from 1 to 16 rows (C0: every dense piece −0.01..−0.1 ms per row), i.e. nothing; a pass skips a layer's weights only if every row skips it, and with drafter-sure runs of ~1 token no 16-row pass is all-sure (the 125B's own runs of 13.7 are the oracle's, not the engine's).
- **The form that can pay.** A layer group that the model does not need for any row: skip its mixer, HC read and MoE for all rows. Prize if 4 / 8 of 48 layers pass: −8 / −17 % of trunk bytes, expert union and kernel count together, i.e. +8-15 % on the realizable design.
- **Must be true.** Some 4-layer group changes the argmax on < 1 % of 125B-sure rows when removed outright. Prior [G]: unlikely (< 30 %): reusing (not removing) the MoE output of 12-23 already costs 0.14 %, and the mixers' reuse 29-88 %; removal is harsher than reuse everywhere the map looked.
- **Test, kill.** One night on the map harness: `skip_L{a}_{b}` for the twelve 4-layer groups on all rows (12 × 4 min), flips by class; kill if no group is < 1 % on code-sure rows (then the lever is closed for this model). QD.
- **TRIED.** L1-09 early-exit KILL (exit after layer 40 agrees 5.7 %) removed the LAST layers and read the head from an intermediate state; the layer-skip self-speculation KILL (1.0-1.2×) was a drafter. An all-row middle skip inside the exact check is a different object; the reason those died (the head needs the final layers; an extra AR pass) does not apply. The prior stays unlikely.

### 4.4 The trunk as the chat drafter (D2): a 2-bit trunk copy with the resident experts
- **Mechanism.** Chat's wall is a ≈ 0.7-0.75 (kept 2.0-2.6 at any width: R-61N). The near-copy (the trunk + 10 % experts) keeps 8.0 on chat [K]. Run a conversion-only copy of the trunk at 2 bits (HC + GDN / attention projections → ~0.7-0.9 GB; router + shared 0.17; fp32 GDN state 0.3) with the resident experts as a sequential drafter; the check stays exact.
- **Bytes / time** [P]. Per draft step ~0.9 GB + resident experts → 3.5-4 ms at the byte floor, 5-7 ms real; a block of 8 drafts 40-55 ms + an 8-row check ~30 ms → ~6 kept per 75 ms → ~80 tok/s today's kernels, ~100-150 at the floor; RAM +1.2 GB. Mission 6's chat ×2.3.
- **Must be true.** The 2-bit copy agrees with the 125B on ≥ 0.85 of chat tokens per step (unmeasured; 3-bit dense untrained is +12.5 % ppl, so 2-bit will be rough: agreement, not quality, is what matters for a drafter).
- **Test, kill.** One night: convert, then teacher-forced agreement on the map's IFEval / multi windows per step (≥ 0.85 PASS; < 0.8 KILL) and a DS-style walk for kept. Exact (the drafter only proposes).
- **TRIED.** "Self-speculation with the resident subset" KILL (each draft a full 27 ms pass): the 2-bit copy removes the reason (0.9 GB, not 3.4); D-07's arithmetic (3.44 GB per step) likewise. Not for code, where DFlash2's 6.3 ms block beats any 5 ms × 16 sequential draft.

### 4.5 The k-head gate (certificate distillation; FLOOR_125B 3.6)
Coverage at zero flips 47.7 % → 70 %+ of code rows: union ×0.75 of the bands' (toward the oracle's ×0.69), SSD likewise; +10-20 % on code at any width [G]. Test queued (MTP Head, Tue): a small head on DFlash2's features predicting the cheap pass's certificate; kill < 60 % coverage at ≤ 0.1 % flips. QD. New (no learned gate in TRIED).

### 4.6 M-18: ranks 0-1 from their 3-bit part on sure rows (SSD by day)
MoonShots measured −54 % SSD MB per kept token on the capture [K]: the day-time SSD cap on code rises from ~460 to ~1,000, so C 256 by day stops being the wall. Must be true: top-2 at 3 bits on cf ≥ 0.999 rows flips ≤ 0.3 % (all-3-bit was KILL by KLD on all tokens; sure rows absorb top-2 at 0.00 %, so the reason may not apply there). Test: a flip arm on the tiered engine (run 8 of FLOOR's experiment). QD.

### 4.7 The fused dense body (exact; Leap's lane, the largest realizable time lever)
C0 [K]: dense 36-38 ms per pass of which GDN 12.4 (2.3× bytes), HC reads 11.4 (5×), attention 7.5, router / shared / tail 5, head 2.5; A1 / A2 / A4 are gone, A3 is in. One-kernel GDN body (L1-15 showed 2.5× on the 35B), fused HC read + norm + router, attention + tail fusions → 15-18 ms (Leap's own accounting); the byte floor 9.5-11.6. Megakernels stay KILL (barriers cost more than dispatches); this is fusion into fewer ordinary dispatches. Prize at the realizable design: 60 → 45 ms per 12.5 kept (+33 %).

### What was examined and found not to break anything (with the reason)
Lookahead / Jacobi (KILL ≤ 5 %, rows cost more than they return); trees (KILL: the drafter's second guess at a knowledge miss is also wrong; cheap rows do not change that); relaxed acceptance (QD, chat only); Skeleton-of-Thought parallel answers (PARKED: changes the answer, f(code) < 20 %); a two-pass self-certified check (oracle-grade predictor but a second trunk read: loses at 45 GB, FLOOR 3.3); 2-bit / 3-bit trunk for the exact track (KILL by quality); lossless weight coding (8.5 % at best, CPU-bound); precision per row (weights are per pass); the ANE or CPU as a second memory path (same DRAM); sticky / slab routing and a 24-layer trunk (training-time; BLUEPRINT).

## 5. The one design to bet on, and the limit
**The bet: the 32-row banded runahead pass.** NAX32 + the k-head gate (cf ≥ 0.999 top-2 and 0.99-0.999 top-5 until the head lands) + runahead + HC8 + the fused dense body + the 4-bit drafter + DFlash3 / HPD; chat on D2; draft-ahead by day. Stacked [P/G]: code today 63.6 → ~110 (gate, HC8, D7b, draft-ahead on today's kernels) → ~200 (fused body 15-18 ms, NAX at 1.3× the floor) → ~260-300 (32-row runahead at kept ~15-17) → ~350 with the k-head at C 320 or with M-18 by day; exact mode on the same engine ~200; chat ~100-120 (D2), math ~220, agent ~130; mixed workload ~150-170 (harmonic, equal shares). Order: the fused body and NAX (Leap; exact, no quality gate, the largest term), the gate's engine build (BigMoE; EvalSuite's same-scores on it decides adoption), the 32-row runahead (MoonShots → Leap → BigMoE), the k-head and HPD (MTP Head), D2 (one night of conversion).
**The limit, precisely.** Every design that verifies the 125B exactly reads the trunk once per pass (≥ 2.7 GB) and the experts' union once per pass (≥ 2.2 GB at 16 rows even for the oracle), and keeps at most kept(B, a) tokens per pass. With every buildable drafter at a ≤ 0.96, kept ≤ 12 at 16 rows and ≤ 18 at 32, so bytes per token ≥ 0.46 GB (oracle gate) and ≥ 0.60 (realizable): ≤ 620 / 470 tok/s on code in bytes, ~300-350 with kernels at 1.3-1.5× the floor. 0.3 GB per token needs kept ≥ 25-30 per pass, i.e. a drafter at ≥ 0.98 per token over 32-64 positions; the only object measured at that level is the 125B's own trunk with its experts (the near-copy 0.983), and a trunk pass per draft is the AR ceiling (62 tok/s). The limit is therefore the model's knowledge at its ~13 % unsure positions, which lives in the trunk and the routed experts and cannot be drafted without reading them. It is broken only by a model whose chaining head is trained with the trunk (BLUEPRINT 3.7) or by a cheaper way to carry that knowledge than 2.7 GB per step, which conversion does not give (3-bit dense +12.5 % ppl; a 2-bit copy is a chat drafter, not a code one).

## 6. TRIED check (idea → the entry → the reason, and whether the new design removes it)
4.1 ← M-16 KILL at 16 rows (the per-row cap; 32 rows left open on β ≤ 2.5, measured 1.7-2.1 today: removed), K-62L KILL (SSD-bound loop: removed by C 256 + the gate), shadow cache KILL (two fixed parts: not this design). 4.2 ← pipelined pre-drafting priced out (GPU on the critical path: removed by SSD-idle scheduling, three candidates, a 6.3 ms drafter); R-70D / Rnd23 are the SSD-prefetch side (window too short / recall too low: not revisited). 4.3 ← L1-09 early exit, layer-skip self-speculation (exit and drafter objects: different; the prior stays unlikely). 4.4 ← D-07 and resident-subset self-speculation (a 3.4 GB step: removed by the 0.9 GB copy; stays dead for code on arithmetic). 4.5 new. 4.6 ← all-3-bit KILL (whole-distribution KLD on all tokens; sure rows are a different object: to be measured). 4.7 ← megakernels KILL (barriers: not this), K-73 ADOPTED, L1-15 PASS on the 35B. Not re-proposed: trees, lookahead, n-gram, exact sampling, 2-bit anything for the exact track, pinning / LFU / learned eviction, mmap, chunked reads, D1 commit, two-pass verify, Skeleton-of-Thought as a 350 route.
