## 0. Verdict in seven lines
1. **The dead ideas share six assumptions** (section 1): the drafter runs on the GPU on the critical path; it starts after the check ends; it is fixed during a session; it is one model predicting tokens; its knowledge lives in its weights; and a check verifies one fixed-length chain. The information bound of DRAFTER_98 is a cost law only for contexts the 125B has not decided before; where it has, its decisions are reusable by lookup at zero trunk cost.
2. **One of them is already broken by the data** [K, drafter_memory_probe.py]: on HumanEval+ code, 58 % of the drafter's tested positions sit inside a verbatim span of ≥ 8 tokens that appeared earlier in the same window, and the token that followed that span last time is right 99.2 % of the time there (the drafter: 96.1 %). A CPU-side override "use the longest match when it is ≥ 8 tokens, else the draft" lifts per-token agreement 0.924 → 0.942, the deep positions from 86-89 % to 95 %, and accepted drafts per check ×1.07 at 16 rows and ×1.38 at 32 rows. It hurts math (×0.95: the match is wrong more often than the drafter there) and does nothing on chat (×1.0-1.03). Prompt lookup was KILL here on agent turns and math (LK1, D-06, M-05, SUFFIX); the reason, few and imprecise matches, does not hold on code.
3. **The other free lever is measured too**: two block drafters picked per position by confidence (DUALDRAFT, live Tuesday) are right together on 94.0-94.4 % of code positions against 90.9 % alone, 92.7 % with the pick [K replay]. The two levers act on different rows (copies and deep positions; mid rows), so they should stack: kept ~12.4 at 16 rows and ~16-18 at 32 on copy-rich code, which is RELAX_350's "kept-13 drafter" without any training [P/G].
4. **Three more ideas with a measured basis and a one-night test**: the Neural Engine shadow drafter (a bigger drafter drafting the next block from the three likely cut points while the GPU checks; MEND-b's kill reason, "drafting is 3-8 % of a check", does not apply because the gain is size and candidates at zero critical-path cost; what remains is 3-10 % of shared bandwidth, priced); online adaptation of the drafter's readout from the check's labels (published as OSD / DVI / OmniDraft, never tried here; the local evidence says small: the same mistake recurs in < 1 % of misses, and offline fine-tunes on own outputs gave no held-out gain); and the match-driven block length (32 rows only inside long copies, where the override keeps ~25-30).
5. **Dead on the data, said plainly**: a misprediction cache (the same context + draft seen at an earlier miss: 0.2-0.9 % of misses); a datastore of the 125B's other answers (8.7 % of code misses at low precision; M-05's +0.08 on math); structural rules for code (indentation: the drafter is already at 97.5 %, the rule at 80.8 %; 9 fixable misses in 6,177 positions).
6. **The bet** (section 3): the session match override + DUALDRAFT + the match-driven block length, as CPU-side post-processing of the drafter's block before the check (exact), with the ANE shadow drafter by day; owners MTP Head (the walks and the ensemble), BigMoE (the post-processing path in the engine), Leap (the ANE latency probe), NewIdeas (the kept ledger per lever on the 98 % track). Expected on HumanEval+-like code: kept 10.5 → ~12.4 (16 rows) / ~16-18 (32 rows); on copy-poor code and math the stack gives ~+10 % only; chat unchanged.
7. **What stops them all on novel text**: the mid-row wall of DRAFTER_98 stands wherever the 125B has not decided the same thing before: math (the match hurts), chat (no matches), and code without copies. There the stack buys +8-15 % (the ensemble), and 0.98 remains the trunk's.

## 2. Five ideas (and three that died on the data)
Expected gains are per class on code unless marked (today: sure 95.5 %, tie 30 %, mid 66 %; by depth 89.8 / 92.7 / 92.5 / 87.5 at 1-3 / 4-7 / 8-11 / 12-15 [K DRAFTER_98]).

### 2.1 The session match override (longest-match ≥ 8 over the window, on the CPU, before the check)
- **Mechanism.** Keep a hash table of every k-gram (k ≤ 16) of the window so far (prompt + accepted tokens) → the token that followed its most recent occurrence. After the drafter proposes a block, walk the block on the CPU: at each position, if the last ≥ 8 tokens (including earlier drafts of this block) match an earlier span, replace the draft with the token that followed the match; keep the drafter's token otherwise. Exact: the check decides. Breaks A4, A5, A7.
- **Closest TRIED and why the reason does not apply.** LK1 (spec125 prompt lookup +1.2 / −0.1 %), D-06 (prompt lookup recovers 10.6 % of agent first misses), SUFFIX (too few long matches on Kamen's turns), M-05 (datastore + lookup on math: +0.08 kept), L1-10 (copy-span rows, BETWEEN): all standalone or oracle co-drafters on agent / math. The measured reason was few, imprecise matches; on code with the 125B's own restated docstrings and signatures, 58 % of positions carry an ≥ 8 match at 99.2 % precision [K]. The override is gated by match length, so it never fires where the reason holds (math: 4.3 % of positions at 70 %; it is switched off there by the type rule).
- **Prior art.** Prompt lookup decoding (Saxena), LLMA, SuffixDecoding, REST: published as standalone drafters; engines combine n-gram drafts with a draft model as options (llama.cpp's docs; vLLM's adaptive n-gram proposer varies the draft length per request). A per-position override by a measured match-length threshold on top of a block drafter: not found as a studied method; new here.
- **Expected gain** [K profile on 24 HumanEval+ windows]: agreement 0.924 → 0.942; by depth 94>94 92>92 91>91 95>94 95>95 93>93 93>94 94>96 94>96 92>96 91>95 91>95 89>94 89>96 86>95; accepted drafts per check ×1.071 at 16 rows, ×1.375 at 32. Math ×0.948 / ×0.939 (off); IFEval ×1.03 / ×1.15; multi ×1.00. By class: the copies are sure rows (the drafter's deep sure-row decay is where the gain lands); ties and mids unchanged.
- **RAM and ms.** Kilobytes; microseconds per position on the CPU, inside the draft-to-check gap.
- **Test and kill.** MTP Head, one evening, CPU: d02b_walk.py with the override on the 24 code windows + MBPP's fresh answers (E2's capture, 52K tokens) + the 12 agent windows; line kept(16) ≥ +6 % and kept(32) ≥ +25 % on HumanEval+, and ≥ +3 % on MBPP / agent; kill < +3 % at 16 rows on code. Then BigMoE: the CPU post-processing hook between the drafter and the check (one flag; the block's ids are already on the host for the gate).

### 2.2 DUALDRAFT: two block drafters in one batched pass, the higher confidence per position
- **Mechanism.** Two drafters (L1-20 and a differently trained twin: seed, data order, or E2's x2) draft the same block in one batched call (the drafter is launch-bound: batch 2 ≈ +1-2 ms); per position the draft with the higher selector softmax goes to the check. Breaks A4. Pre-registered by MTP Head (REPORT 'DUALDRAFT', Tue by day).
- **Closest TRIED.** L1-06 joint verify (both chains in one check, keep the longer: KILL, +9.2 % oracle for 8 → 15 rows); D-19 bandit switch (per prompt: KILL); TYPERULE (per prompt: PASS). The per-position pick costs no rows and no switch latency, which is what killed L1-06 and D-19.
- **Prior art.** TAPS (ICML 2026) routes among specialized drafters by confidence per draft tree; MetaSD (2026) and HedgeSpec (2025) pick a drafter per block or per query with bandit / no-regret feedback. Per-position selection among drafters' top-1: not found; new at that granularity.
- **Expected gain** [K replay, drafter_ensemble.py]: near-identical variants: union 94.0 / 94.4 %, pick 92.7 %: sure 95.5 → 96.9, mid 66 → 70; with diverse drafters the union grows [G]: kept +8-15 % at 16 rows.
- **RAM and ms.** +0.24-0.47 GB per extra drafter (4-bit / bf16); +1-2 ms per block.
- **Test and kill.** Tuesday's pre-registered walk (kept(16) ≥ 11.3, i.e. ≥ +8 %); then the walk with 2.1 stacked (line: the gains add to within 2 points).

### 2.3 The Neural Engine shadow drafter (a bigger drafter, off the GPU, drafting the next block from the three likely cut points during the check)
- **Mechanism.** A 1B-class block drafter (int8, CoreML) runs on the Neural Engine while the GPU checks block i, drafting block i+1 from three prefixes: the block end and the two lowest-confidence positions of block i. When the check ends at one of them (70 % of code checks [K]), the next draft is ready at zero critical-path cost; otherwise DFlash2 drafts as today. Breaks A1 and A2.
- **Closest TRIED.** MEND-b (drafter on the Neural Engine: KILL on paper, "drafting is 3-8 % of a check and must wait for the check's result"), Mirror-SD (PARKED / KILL, ≤ 6-9 %), SD-cap (bigger drafters: cost grows with layers). The 3-8 % reason priced only the saved draft time; here the prize is the bigger drafter's accuracy at zero path cost, and "must wait for the result" is met by drafting from predicted cut points (A2). SD-cap's cost reason leaves the critical path; what stays is the shared memory bandwidth and the training cost.
- **Prior art.** A blog (fazm.ai) claims a ~1B drafter on the Neural Engine beside a GPU verifier, no benchmark; CoreML's RangeDim supports variable-length draft and verify shapes; PEARL (2024) overlaps drafting with verification on GPUs. New as a measured design.
- **Expected gain** [P/G]. Size: SD-cap's +6 % tokens per 1.6× layers gives a 1B (2× layers) ~+9 %, 2B ~+15 %: mid rows 66 → 72-75, deep sure rows +3-5 points; the hidden draft +5-10 % by day. Cost: a 1B int8 drafter reads 1 GB per candidate: 3 candidates per ~100 ms check = 30 GB/s, ~10 % of the 284 GB/s the check streams [K bw_probe], so the check slows ~5-10 %; one candidate (the end + the lowest cf cover ~60 % of checks) ~3 %. Net +5-15 % by day, ~+5-10 % at night. The ANE's own throughput for a 1B int8 block of 16-32 positions is the unknown (tens of GOPS to tens of TOPS depending on the op mix) [G].
- **RAM and ms.** +1 GB (int8 drafter) + CoreML buffers; 0 ms on the critical path if the ANE finishes within the check.
- **Test and kill.** Leap, 10 minutes: DFlash2 L1-20 converted to CoreML int8 on the Neural Engine, one 16-row block: latency (kill > 30 ms) and the GPU's warm check time while it runs (kill > +10 %). Then MTP Head: whether a 1B drafter is trainable on the laptop (D-09's recipe at 2× layers, one night) or needs the free cloud.

### 2.4 Online adaptation of the drafter's readout from the check's labels (fast weights, on the CPU)
- **Mechanism.** Every check returns the 125B's exact token at each verified row and its top-k. Keep a small fast-weight correction on the drafter's output layer (a low-rank delta on fc, or a per-session logit bias table keyed by the drafter's hidden state hash), updated with a few SGD steps on the CPU during the next check, from the last checks' (features, label) pairs. Breaks A3.
- **Closest TRIED.** L3 / L4 / REGENFREE (offline fine-tunes on own or Claude outputs: no held-out gain), HPD-1 (the set is fit), E2 (fresh on-policy data: +0.22 kept per doubling), K-HEAD (a head on the drafter's features does not beat its cf). Their reason, held-out turns differ from training turns, does not apply to adapting within the same session; K-HEAD's reason (no extra margin information in the features) applies to the gate, not to token correction.
- **Prior art.** Published: Online Speculative Decoding (Liu et al., ICML 2024: the draft model is re-distilled from the target's outputs with spare compute), DVI (2025: a self-speculative head trained online from accept / reject signals), OmniDraft (2025: online adaptive drafter). A 2025 domain study found offline distillation beats online by 11-25 %. Not tried in this project.
- **Expected gain** [G, bounded by K]: the within-window repeat rate of the same mistake is 0.2-0.9 % of misses, and E2's slope prices a session's few thousand tokens at ~+0.02-0.05 kept; so +1-3 % on code benchmarks; long agent sessions with recurring identifiers and paths could be +5-10 %, unmeasured.
- **RAM and ms.** Megabytes; 1-5 ms of CPU per check, hidden in the check.
- **Test and kill.** MTP Head, one evening: on the 12 agent windows (2,215 positions each) and the 24 code windows, adapt a logit-bias / low-rank fc delta on the first half of each window's verified tokens, walk the second half; line kept +5 %; kill < +2 %.

### 2.5 The match-driven block length (32 rows inside long copies, 16 outside)
- **Mechanism.** The CPU knows, at draft time, how much of the drafted block is covered by ≥ 8-token matches (2.1). If ≥ 24 of 32 drafted positions are inside such spans, the check takes 32 rows; else 16. Breaks A6.
- **Closest TRIED.** AW1 (adaptive width by a verify-cost table: ADOPTED), L1-14 (confidence cut t 0.3: ADOPTED), NEW-3 (confidence-adaptive length, priced +3-4 %). This one uses predictability from the context, which no width rule here used.
- **Prior art.** Adaptive draft length by confidence is published (SpecDec++, AdaEDL, CALSTOP KILL here as a stop rule); by match coverage: not found.
- **Expected gain** [K profile + P]: inside long copies the override holds 95-99 % flat, so a 32-row block keeps ~25-30 there (the profile model's ×1.375 at 32 rows is the window-wide average of copy and non-copy blocks); outside copies 16 rows at today's 10.5. On HumanEval+ code the average kept per check rises to ~16 (×1.55 over today's 16-row 10.5) at the 32-row check's cost (+5 ms dense, rows ×2) only on the copy blocks [P].
- **RAM and ms.** Nothing beyond 2.1.
- **Test and kill.** The same walk as 2.1 with the length rule; line: kept per check-ms ≥ +10 % over 2.1 at 16 rows; kill < +4 %.

### Died on the data (drafter_memory_probe.py) [K]
- A misprediction cache (branch-predictor style: the same last-3 tokens + draft seen at an earlier miss, corrected to the same token): 0.2 % of code misses, 0.8 % math, 0.4 % IFEval, 0.2 % multi; false positives as many. Mistakes do not repeat within a window.
- A datastore of the 125B's own other answers (leave-one-out, 24 code windows): ≥ 8 matches on 4.6 % of positions at 83.6 % (the drafter 95.8 % there); 8.7 % of misses recoverable at low precision. M-05's +0.08 kept on math stands.
- Structural rules for code: on the 443 indent-after-newline positions the drafter is right 97.5 %, the rule ("the previous line's indent, +4 after a ':' line") 80.8 %; the rule fixes 9 of the drafter's 11 misses there, 0.15 % of positions. Punctuation and bracket rules will be the same: the drafter has learned the syntax.

## 3. The bet, the plan and the owners
**The bet: CPU-side post-processing of the drafter's block before the check, exact, three parts: the session match override (2.1), the per-position pick between two drafters (2.2), and the match-driven block length (2.5); the Neural Engine shadow drafter (2.3) by day; online adaptation (2.4) only if its within-window test pays.** Expected on HumanEval+-like code [P/G]: agreement 0.924 → ~0.95; kept 10.5 → ~12.4 at 16 rows and ~16-18 with the length rule; on copy-poor code and math ~+10 % (the ensemble alone); chat unchanged (the chain and the tie rule are chat's levers). With RELAX_350's floor engine this is ~290-330 on code at the twin's quality level and ~350 with a 3 % rule, from drafter work that costs no training.
Ranked plan:
1. **The override walk** (MTP Head, one evening, CPU): 2.1 on the 24 HumanEval+ windows, E2's 52K MBPP tokens and the 12 agent windows; kept(16) and kept(32); lines in 2.1.
2. **DUALDRAFT live** (MTP Head, Tuesday, pre-registered): then the stacked walk (2.1 + 2.2).
3. **The length rule in the same walk** (MTP Head): 2.5.
4. **The engine hook** (BigMoE): the drafter's block → CPU override / pick → the check; one flag; token equality vs REF2-T on every arm (the drafts change, the tokens cannot).
5. **The ANE latency probe** (Leap, 10 minutes): 2.3's kill lines; then the 1B drafter question (MTP Head).
6. **The within-window adaptation test** (MTP Head, one evening): 2.4.
7. **The kept ledger** (NewIdeas, the 98 % track): one table of kept per check per lever and domain, so the stack's arithmetic is checked against walks, not assumed.
**What stops them all on novel text**: on math the match model is wrong more often than the drafter at every length; on chat matches cover 4-7 % of positions; on code outside copies the mid-row wall of DRAFTER_98 stands (66 % at the 125B's own uncertain decisions, capacity-bound). There the ensemble's +8-15 % is the ceiling of free levers, and 0.98 stays the trunk's.
