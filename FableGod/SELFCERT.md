# SELFCERT — can the 125B certify itself mid-pass? A CPU screen (FableGod, mission 21, Mon 2 Nov 2026, 18:2x-18:3x EET)
Marks: [K] measured here (source named), [P] arithmetic on measured numbers, [G] judgement. Rules kept: CPU only (selfcert_probe.py, 57 s), no GPU, no downloads, writes only in ~/FableGod. Short, as asked: a screen.
Data [K]: the 125B's five taps per position (layers 5 / 15 / 25 / 35 / 45, the mean of the 4 HC streams, fp16, 2,560-wide) with each row's top-32 log-probs exist today for GSM8K (60 windows), IFEval (30) and multilingual (24) in ~/TrainLab/data/d02a; not for code. EARLYTAP (MTP Head, tonight) re-extracts code taps but, as pre-registered, stores h = hidden_norm(fc(taps)) for three tap sets, not the raw per-layer taps; a per-layer probe on code needs the raw taps kept (one flag in taps_extract.py). The screen therefore ran on math and IFEval, held-out by window (45 / 15 and 22 / 8), on the rows the drafter reaches (so the cf baseline is on the same rows), ~120 rows per window, 4,115 / 1,412 (math) and 1,247 / 397 (IFEval) rows; the probes are logistic on the standardised 2,560-dim state per layer (6 epochs, averaged), the fusion a logistic on the layer-35 score, cf, cf ≥ 0.999, copy state (≥ 8-token in-window match) and the draft token's kind.

## 0. Verdict in five lines
1. **KILL at the screen's line, on the data that exists** [K]: at ≤ 0.1 % false certificates the layer-35 probe covers 1.6 % of math rows and 0.8 % of IFEval rows (the pass line was 80 % at a layer ≤ 35; the kill line 70 %); layer 25 covers 0.5 / 3.0 %, layer 45 covers 6.1 / 5.8 %. The drafter's cf covers 28.7 % (math) / 7.3 % (IFEval) on the same rows at the same line; the oracle (the sure share) is 86.0 / 27.0 %.
2. **The state knows sureness roughly, not purely**: the probes order sure before not-sure rows 83-85 % of the time at layers 25-35 and 94 % at layer 45 (an AUC-like share of pairs), and at a loose line (≤ 2 % false) layer 45 covers 68 % of math rows; at the strict line a few confident errors at the top collapse the coverage, the same over-certification that killed the k-head (56 %, 0.57-0.70 % flips on held-out windows).
3. **Fusion adds nothing**: layer-35 score + cf + copy state + draft kind covers 3.5 % (math) / 0.8 % (IFEval) at ≤ 0.1 %; cf + copy state alone 4.2 / 1.5 %. On these rows the cf is the best single certificate and the mid-layer state does not lift it.
4. **What it means**: the single-pass mid-layer gate (top-2 experts for layers L+1..48 on rows the layer-L state certifies) does not open on this evidence; the two-pass check (CACHE.md: 1.25 GB per check at 12 GB with the cheap pass's own p1 as the certificate) stays the realizable 12 GB lever, and the 45 GB gate stays the cf gate. The cheap pass's own p1 remains the only mid-computation certificate that is clean (73.4 % at top-2, 89.8 % at top-5, 0 flips [K FLOOR]).
5. **What could still change it, and the cost**: code taps (not yet extracted raw), an MLP with ~30K rows on the GPU (one evening, MTP Head), and a better operating point (the strict line is coarse at 1,412 test rows: one false certificate is 0.07 %). The jump needed is from ~2 % to 80 % coverage at the same purity; L1-09 (5.7 % token agreement from layer 40), R-32 (a layer-12 probe no better than the drafter's features) and this screen point the same way. Prediction for the code run [G]: KILL at 80 %, with layer 45 near 10-20 % at ≤ 0.1 %.

## 3. The pipeline for code (ready)
selfcert_probe.py loads d02a-format files (f [n, 5, 2560] fp16, lp [n, 32], ids, gen) and the HPD-0 walk's cf per row; `python3 -I selfcert_probe.py code` needs only a `tf_code_*` set in the same format and the walk's names to match. If EARLYTAP keeps the raw taps (one flag), the code screen runs in a minute; its pre-registered lines are the brief's (PASS ≥ 80 % at a layer ≤ 35 at ≤ 0.1 % false; KILL < 70 % at layer 35). The next GPU step, only on a surprise: an MLP probe on the 109 windows' ~30K rows (MTP Head, one evening), judged on the 100 MBPP answers.
