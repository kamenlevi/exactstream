## 0. Verdict in seven lines
1. **The oracle floor on code is ~0.17 of the exact expert bytes** (80 expert records per token instead of 480; 218 MB vs 1,056 at the 45 GB tiers) [P on K]. In a 16-row check it is 0.18 GB of expert reads per kept token at 12.5 kept against 0.67 exact [P; the replay reproduces the engine's measured 8.02 GB per exact check within 4 %]. With the dense trunk (3.3 GB per check = 0.26 GB per kept token; 0.22 with HC8) the oracle totals **0.40-0.44 GB per kept token, and reaches 0.3 only at kept 15-16 with HC8**. The "≤ 0.3 GB, 1,000 tok/s" world does not exist for the 125B on this Mac at any RAM size: the trunk is half of the oracle's bytes, and the floor engine's non-expert time (dense 9-12 + draft 4-6 + start-up 2-5 ms per check) caps even the oracle near 300-380 tok/s on code at 45 GB [P].
2. **The realizable floor with today's predictor is 0.66 GB per kept token on code (0.61 with HC8): 350 is inside the bytes by 1.3-1.6×, no longer at the edge** [P on K]. By the drafter's own confidence band: ≥ 0.999 (47.7 % of code rows) takes top-2 at **0 flips in 1,607 rows**; 0.99-0.999 (17.9 %) takes top-5 at 0 flips in 604; the rest stays exact. Expert reads ×0.58, expert pairs ×0.48, SSD misses ×0.46 at C 256 (replay) [P]. DAY9's independent runs landed while this was written and agree: Breakthrough's gated run (top-2 only on drafter-sure rows, the rest exact) flips 0 of 1,607 gated code rows at cf ≥ 0.999 and 2 of 2,211 at 0.99 [K, DAY9_q1.txt]; MoonShots' bytes capture on the live engine's checks gives the expert union −28.7 % at 0.999 and −40.8 % at 0.99 against this replay's −29 % / −41 % [K, band45_capture.txt], with SSD MB per kept token −28 % / −40 % at C 256 + M-17 and today's engine implied at 63.6 → 71-76 tok/s. On chat the same bands are 8-9 % of rows, so the cuts save 5-21 % there and chat's floor stays the drafter's kept per check.
3. **The realizable-to-oracle gap is 2.2× in expert bytes and 3.6× in SSD misses, and it is NewIdeas' UGB gap again:** the drafter is sure (cf ≥ 0.99) on 65.7 % of code rows, the 125B on 86.8 %; at zero flips the drafter's gate covers 55 % of what the oracle covers. Of three realizable predictors measured here, the cheap pass's own p1 is oracle-grade (a top-5 pass whose p1 ≥ 0.9: 89.8 % of code rows, 0 flips, every 125B-sure row covered) but costs a second dense pass (priced out at 45 GB, marginal at 12 GB); routing agreement with the previous position carries no signal (KILL); the previous row's class is 93 % predictive on code but only across checks.
4. **Tok/s on code** [P; floor-engine model of ROUTE_350 with the measured pair / byte / miss ratios]: 45 GB: exact 137 → realizable 208 (C 256), 237 (C 320), 269-323 with the best fixed terms at kept 12.5-15; oracle 302 / 319 / 379-455. 24 GB, SSD-capped (replay, ~1.3× pessimistic vs the engine): exact 59 → realizable 127 → oracle 418. 12 GB: exact 18 (engine measured 23-27) → realizable 46 → oracle 169. Mixed workload (equal shares of code / math / chat / agent, harmonic): realizable ~130, oracle ~170 [P/G].
5. **Cuts combine by adding margin loss, not by union** (the additive model over-predicts sure-row flips 1.6-1.9× and matches mid rows): middle-layer reuse (8-35, one row old) does not stack on top-2 on the same row (predicted 5-15 % of code-sure rows vs 1.2 % if the flips were a union; stage 2a's `moe_reuse_chain1_L08_35_topk2` measures it today), so the oracle takes top-2 OR reuse per row and reuse adds only 13 % beyond top-2 everywhere. Precision per part is exhausted: HC8 (−0.6 GB per check, DAY9 #3) is the last weight-precision lever; 4-bit outputs of attention / GDN / HC are free on sure rows but save no weight bytes.
6. **The mechanism exists** (gate_bands in dm_common.py: per-row k through the sync-free gate, no renormalisation, exact mode = k 10 everywhere, bitwise), and its quality cost has the int4 twin's profile, not a clean zero: the gated rows do not flip, but the exact rows downstream see a changed context and flip 1.25 % of all code rows at cf ≥ 0.999 (3.97 % IFEval, 2.50 % multi) [K, gated run], of which on code 20 of 42 are ties (p1 − p2 ≤ 0.1, 40 % of the ties flip), 21 are mids (5.4 % of them) and 1 is a 125B-sure row (1 of 1,320) [P on K]. Nearly every answer is touched at some tie or mid token (11 of 12 on code), as the twin touches ~1 % of code tokens with identical scores. So "exact by scores" is EvalSuite's call on the same-scores test, as it was for the twin and the 3-bit tiers; the band rates alone can be certified (≥ 15,000 band rows at 0 flips bounds them at ≤ 0.02 % per token), the sequence-level deviation cannot be made zero by any gate, because the cut rows' hidden states feed the exact rows.
7. **The one experiment** (one night on the map harness, section 5): the realizable banded check teacher-forced on ~30K code rows plus GSM8K, agent and more chat windows, with the router scores and the per-row p1 under the cut logged, plus the CPU bytes replay on the captured routing. It decides between "350 with a 1.3-1.6× bytes margin" and "350 at the edge"; by construction it cannot produce a 0.3 GB world, and the best new lever it leaves is a drafter-side k-head trained on the cheap pass's certificate (section 3.6, NEW).

## 1. Method, and what is measured versus computed
- **Per-row re-reading [P on K].** For each of the 10,316 rows: the 125B's class (sure p1 ≥ 0.99 / tie p1−p2 ≤ 0.1 / mid), the drafter's band (cf ≥ 0.999 / 0.99-0.999 / 0.9-0.99 / < 0.9 / none = the bonus row after 15 kept), and under each cut whether the argmax flipped and the margin of the baseline token (its log-prob minus the best other; a bound when it left the top-8). The re-reading reproduces report.md's flip table exactly (floor_rows.out table 1), so the join is right.
- **Bytes [P on K].** From the routing capture, the union of expert ids per layer over each 16-row block of answer rows under a scheme (k per row; rows that reuse post nothing on layers 8-35), summed over 48 layers; bytes at the 45 GB tiers (ranks 0-1 at 2.8 MB, ranks 2-9 at 2.1 MB; TRIED: top-10 × 48 × 2.2 MB = 1.06 GB per token). Exact mode gives 8.37 GB per 16-row block against the engine's measured 8.02 GB (REF2-T) [K]: +4 %. The union per layer is 76.6 (code), not the 92 of the 10·N^0.8 law used in ROUTE_350; the law's bytes were right because its per-expert size was low. An LRU replay per layer (C slots; prompt rows exact and warming the cache; answer rows in 16-row blocks) gives misses per kept token; its exact-mode numbers are 1.25-1.4× the engine's measured ones (C 256: 45.5 vs 36 misses per kept; C 320: 23.5 vs 17.2), so absolute replay caps are pessimistic and ratios between schemes are what to use.
- **Combined cuts [P, model].** Margin loss per cut on the baseline token, summed over cuts, flip predicted when the sum exceeds the row's margin. Validated on the one measured combination (layers 12-35 at once vs its halves g1 + g2, lag 1): code-sure predicted 1.64 % vs measured 1.03 % (union of the halves' flips: 0.24 %), IFEval-sure 3.35 vs 1.77, multi-sure 0.63 vs 0.69; mid rows 34.3 vs 33.0, 35.1 vs 39.8, 24.5 vs 29.7. So the model is conservative on sure rows by up to 2× and right on mid rows; its per-row precision is poor (13 of the 30 measured code-sure flips predicted, 48 predicted), so it is used for population rates, not for choosing rows.
- **Caveats carried from the map [K]:** every row ran perturbed, so the context is perturbed too (upper bounds for any scheme that keeps unsure rows exact); the 4-bit D-02a configuration, not the 3-bit tiers; 12 windows per domain; teacher-forced on the 125B's own answers; the drafter's cf is the walk's, without the t 0.3 cut (2-4 % of kept rows differ).

### 3.5 What would close the 2.2× gap
A predictor that recovers the 125B-sure rows the drafter is unsure about (25 % of code rows). Candidates, in order of evidence: (1) the drafter's confidence re-calibrated against the certificate rather than against its own correctness (3.6); (2) the router's top-2 mass per layer (unmeasured, logged tonight); (3) the mission-8 HPD data route, which makes the drafter sure on more rows as a side effect of making it right there.

### 3.6 NEW — certificate distillation (a k-head)
Train a small head on the drafter's features (DFlash2's five taps, or the trunk's HC readout the native head sees) to predict the cheap pass's certificate ("p1 under top-2 ≥ 0.99" / "under top-5 ≥ 0.9"), not the drafter's token correctness. The labels are free: any top-2 / top-5 teacher-forced run produces them (10,316 rows exist now; DLOG + one map run per day gives ~100K per day). Why it can beat the cf gate: the UGB kill says the drafter's token confidence is low exactly where the 125B is sure but the drafter's own choice is hard; the certificate asks a different question (will the 125B's argmax survive top-2?), which the 125B's own hidden state answers 100 % of the time on sure rows and which is known to depend on the row's margin, a quantity the drafter's features carry imperfectly but not at the token-identity level. TRIED has no learned gate or k-head (CALSTOP was a stop rule; UGB used the raw cf). Prize: coverage at zero flips from 47.7 % toward 86.8 % of code rows, i.e. up to the full 2.2× on expert bytes (code 208 → ~300 at 45 GB; 12 GB ×3.6 on misses) [G]. Cheapest test (MTP Head, one evening, CPU or small GPU): logistic / 2-layer head on the existing 10,316 rows' drafter features with cross-validation; report coverage at zero flips on held-out code rows. Kill: coverage < 60 % of code rows at ≤ 0.1 % flips (the cf gate gives 47.7 %).

## 4. The mechanism and its quality cost
### 4.1 Engine design [P/G, on the measured pieces]
- One check, one gate: each of the 16 rows carries k ∈ {2, 4 or 5, 8, 10} chosen by the drafter's confidence band for the draft it verifies (the bonus row and rows with no draft: 10). The ids go as GPU data through the existing sync-free gate; the gate masks ranks ≥ k **without renormalising** (renorm is 11× worse on code-sure: 2.33 % vs 0.21 %). Rows at k = 2 touch only ranks 0-1, both 4-bit, so no 3-bit record is read for them.
- What shrinks: expert pairs ×0.48 (the ALU-bound part of the row cost), the union per layer ×0.58 (bytes), the ids posted to the cache ×0.46 in misses at C 256 (M-17's per-layer pools see fewer ids). What stays: the dense pass, the drafter, the combine, the start-up; the OOO order and the LY=8 combine.
- Exact mode is the band assignment "all rows k = 10": bitwise the baseline (topk10 through the wrapper: 0 flips, max |Δlp| 0.0 [K]). One engine, two modes; the published exact numbers come from the same binary.
- Band 3 (0.9-0.99) at "ranks 0-3 at 4 bits" is dropped: in the tiered engine it costs sidecar reads and gains nothing over Q1 at 0.99 (MoonShots' Q2 bytes: −37 % vs −40 %) [K]; that band runs at the standard tiers (top-8) or exact, and its quality is the mid-band question of section 5. MoonShots' M-18 lead (ranks 0-1 served from their 3-bit part on sure rows, −54 % SSD MB per kept token) needs a flip arm on the tiered engine, which the 4-bit map cannot give; it is run 8 of section 5.
- Not in it: reuse (not stackable, 2.2), the two-pass certificate (priced out at 45 GB), any change to weights, expert count or vocabulary.
- Follow-ons it makes cheaper: NEW-3's adaptive block length (rows at ~1 ms make 24-row blocks pay on confident stretches); the 32-row runahead (its re-check rows cost half).

### 4.3 Quality cost under EvalSuite's rules, and which cuts count as exact by scores [K / P]

- What that is: the twin's profile.
