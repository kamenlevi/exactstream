## 0. Verdict in five lines
1. **#1 pre-route on the partial sum (SSD, EXACT): needs-GPU; the pick for the exact track.** No recording holds per-layer partial MoE outputs, so its premise (recall ~0.9 from layer L's output minus the in-flight experts, against R-57's 0.69-0.79 from L's input) is untestable tonight. One 10-minute capture settles it (section 1). Prior art: look-ahead routing from an earlier state is ours (V1 / W1 / CORR / R-57 / R-57b-R) and published (Pre-gated MoE, ISCA 2024, a trained pre-gate on the current layer's state; SiDA, MoE-Infinity, ExpertFlow predict from traces); routing on the *partial output* is a later state, a refinement, not a new kind. Its lead time is OOO's own miss wait, which is why it can pipeline the SSD queue one layer deeper. Value if the recall holds: cloud's chain 22 -> 4-5 ms, -8 halved [G until captured].
2. **#2 sketch-on-miss (SSD, FAST): needs a map arm; the pick for the FAST track, and the largest priced gain.** The map's expert-cut arms bound its deviation: dropping ranks 6-10 outright flips 0.00 % of code-sure rows, 8.6 % of code-mid, 0.07 % of multi-sure, 14.5 % of multi-mid [K]; a rank-32 shadow replaces one missed low-rank expert, not five dropped, on ~15 % of rows (1.6 % of expert uses x 10), so the deviation is <= 0.03 % of code tokens and <= 0.25 % of chat tokens even if the shadow were worthless [P]: cloud's 0.05 % holds as a bound on code. The RAM is the cost: 2.8 GB of shadows displaces ~1,200 exact experts (C 320 -> ~295), +15 % misses [P on cache_replay's slope], all served by shadows. Gain: the exposed SSD per check today is 162-367 ms at C 160 and ~45 ms at C 256 (257 misses x 2.3 MB at 13 GB/s) [K C0, cache_replay]: shadows make it ~2 ms, -10 to -20 ms halved at C 256. Prior art: HOBBIT (serve a miss with a lower-precision copy, backfill exact: the same move with precision instead of rank), Fiddler / ExpertFlow (serve misses elsewhere), SVD-compressed experts; the 12 GB frugal kills (LATE RANK 1: KLD +5.5 %) skipped or deferred ranks, a harsher cut than a rank-32 substitute. Not new in kind; untried here in this form.
3. **#5 MTP-seeded block drafting (kept, EXACT): KILL as proposed, dominated as a pick [K replay].** On the same 666 code checks the native head's depth-1 token is right at the block start 0.865, DFlash2's row 0 0.941 (block starts sit after misses, in hard regions; cloud's 0.94 vs 0.898 reverses there); always seeding loses: code -3.8 %, ifeval -11.9 %, math -8.8 %, multi +3.3 %. A cf-gated pick (seed when DFlash2's row-0 cf < 0.8) gives code +0.1 %, math +1.0, ifeval +2.5, multi +11.5 (the oracle pick +1.3 / +3.5 / +12 / +19), before the MTP call's ~2.2 ms per block and before halving: nothing on code and math, and on chat it is a weaker form of the chat drafter switch already measured (D-23c: the MTP chain keeps 2.54-2.91 on chat against DFlash2's 2.03-2.06). Prior art: our DUALDRAFT per-position pick (mission 17 / 22) and D-22 / D-24; the seeded continuation is a teacher-forced upper bound here.
4. **#6 lookahead-consistency acceptance (kept, FAST): needs-GPU (the walk missions 24 and 25 already asked for); the proxy says the exchange rate improves and the gain halves.** The veto needs the 125B's row r+1 conditioned on the draft token, which no recording holds. Under the true prefix, R1(0.5)'s accepted-but-wrong tokens have a sure next row 19.5 % of the time on ifeval and 29 % on multi, its accepted-and-right near-ties 36-38 % [K relax_positions]: a veto on "next row sure" would cut deviations by ~70-80 % and keep ~36 % of R1's extra acceptances, so IFEval's x1.17 at 3.69 % deviation becomes ~x1.06 at ~0.9 % (halved x1.03), a better rate, a smaller gain; whether the draft-conditioned next row is surer or less sure than the true one is the open question and the point of the walk. Prior art: this is block verification's criterion (Sun et al. 2024: accept by the joint probability of the block) restricted to two tokens under greedy decoding, with Medusa's typical acceptance and Judge Decoding as the FAST-acceptance family; new as a rule here, not in kind.
5. **The pick:** build #2's map arm first (Breakthrough: rank-32 SVD shadows of the real experts, a day of CPU, then the map at a 15 % row-miss rate by class; EvalSuite's same-scores after) because it carries the largest priced SSD gain and its bound already clears the quality bar on code; run #1's capture beside it (BigMoE or Leap, 10 minutes of GPU) because it is exact and decides the exact SSD route in ten minutes; store the check's top-8 per row in the next walk (MTP Head) so #6 and mission 24's test are answered together; drop #5.

## 1. #1 pre-route on the partial sum (EXACT)
What is recorded: expert ids per (token, layer, rank) for the map windows (decision_map/out/routing), the taps at five layers (d02a), no hidden states at MoE boundaries, no partial sums. So the recall from the partial output cannot be replayed. **The capture (BigMoE's r57 loop or Leap's C0 harness, the 12 code map windows + 6 chat, 16-row checks, 10 minutes):** at every MoE layer L, after the resident experts' combine and before the misses land, form the partial output (residual + the resident experts' weighted outputs; in a warm run, simulate the misses by removing each row's experts of rank >= 3, or the experts the LRU would hold cold at C 256), run layer L+1's HC read and router on it, store the top-10 per row; also store the true top-10 of L+1 and R-57's forecast (from L's MoE input) on the same rows. **Line:** recall@10 of the true top-10 >= 0.85 with ranks >= 3 missing (and >= 0.90 with only ranks >= 6 missing) = PASS, build it into OOO's phase 2 (issue L+1's reads at that moment); < 0.75 = KILL (no better than R-57's corrected 0.693 / V1's 0.72-0.79). Where it would act: the demand-SSD chain per check (C0: 162-367 ms at C 160; ~45 ms at C 256 [P]); the lead it buys is one layer's miss wait per layer, so cloud's "22 -> 4-5 ms" is a bound for the part of the chain that is sequential per layer [G]. Both tracks: exact.
