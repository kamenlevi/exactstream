## 2. A pipelined loop, priced (pillar 3)
While the target checks block N, the drafter drafts block N+1 as if all of block N will be kept.
- **It can hide the draft on only ~half of the checks.** The early draft is usable only if the whole block is kept AND the
  drafter's guess for the bonus token is right: q = 0.98^32 = 0.52 at a flat 98 %. On the other 48 % the next block is
  drafted after the check, as today.
- **It pays only if the overlapped draft slows the check by less than q (~52 %) of the draft's own time.**
  - Pipelined cycle = check + kappa x draft + (1 - q) x draft + overhead.
  - Sequential cycle = check + draft + overhead.
  - So it wins iff kappa < q, where kappa is the share of the draft's own time that it adds to the check.
- **On one GPU our earlier measurements say kappa is near 1.**
  - Two NAX6 calls on two GPU streams were only 1.2-2.4 % faster than serial at 32 rows, and 4.7-5.8 % at 16 (NAX-OCC).
  - A draft on a second MLX stream hid none of the commit replay: 0.06 ms per cycle (R-11 D, KILL).
- **At the floor, the draft's bytes add in full**, because bandwidth is shared. Today's chain head reads ~170 MB per step,
  so 32 steps read 5.4 GB per block. That is >= 19 ms per cycle even when perfectly overlapped.
- **The speculative block is drafted from a state one block old.** Its guesses sit at depths 33-63, not 1-31.
  - At 95 % there (98 % at 1-31), pipelining loses to sequential: 204 vs 241 tok/s for the chain head at the floor check,
    321 vs 355 for a one-pass block drafter.
  - Pipelining needs a drafter that holds its accuracy to ~63 deep.
- **Rollback is cheap; the redraft is not.**
  - On the target, the rollback is today's commit replay, unchanged. Capture-commit replays only rejected windows, so it
    is skipped when the whole block is kept, which is the case where the early draft is used.
  - On the drafter, discarding the early draft is a cache trim (~0 ms). Its wasted work is already counted in kappa.
  - The real cost of a miss is the serial redraft (1 - q = 48 %).

**Pillar 3 verdict from the desk: pipelining is a second-order lever.**
- The first-order lever is the drafter's own cost per block: serial ms and bytes.
  - With today's chain head, even a perfect pipeline caps near ~250 tok/s at the floor check.
  - A one-pass block draft or a chain step <= ~0.5 ms and <= ~60 MB is worth more than any overlap.
- The per-cycle overhead matters as much.
  - The batched commit replay (R-12's exact spin-off) is -2.5 ms.
  - The GPU's idle seams between checks (2.5-3.6 ms at SB 2) are the other part.
- **UPDATE Sun 01:2x: Sandbox98's depth-63 read-out (54b4b10) says keep 32 rows as the design point.**
  - With today's drafter, 48- and 64-row checks keep exactly what 32 rows keep (MBPP-50 4.32 / 4.32 / 4.32,
    HE-30 6.24 / 6.26 / 6.26): the chain almost never strings 31+ right guesses.
  - Even a perfect fresh state adds only +3 % (MBPP) / +13 % (HE) kept at 64 rows.
  - So the deeper-check figures below (499-521 / 402-429) assumed 98 % held to depth 63, which today's drafters don't do.
    The same goes for pipelining's speculative block at depths 33-63.
- **Deeper checks beat pipelining, if the drafter holds 98 % that deep.**
  - At the floor, 48 / 64 rows (union extrapolated, [P]) give tau 31.0 / 36.3 for 62 / 70 ms. That is 499 / 521 tok/s
    with free drafting, or 402 / 429 with a one-pass block draft, against 355 at 32 rows.
  - It needs the gate wider again and a pool above 256 per layer (more than 45 GB), since step 0's 32-row max is
    already 242.

**Pillar 2 (the check)**

*The 17-32-row path, design (Sun 01:1x).* REF2's verify forms are certified per row for 1-16 rows: each row equals the
1-row AR. Above 16 rows every form falls back to stock MLX, which is not exact. ref2.py gates them all at R = 16:
- dense (_qmm, _dnr_qmm, _lin);
- the HC read (_gr) and hc_write;
- attention (_att, _verify_sdpa, att_rope);
- GDN (gdn_exact, gdn_body, the gated norm, in_proj_x);
- the expert tiers and slot call.

The design is exact by construction: it reuses the certified forms.
- **Row-local ops** (projections, norms, router, HC read / write, shared expert) take one 32-row call where a per-row-exact
  32-row form exists, and two 16-row calls where none does.
  - **4-bit big shapes: D32's mr2.** D32 measured it on 10-26: bitwise with the 16-row path per row at every K split,
    padding-independent, dense 17.96 -> 22.19 ms per check (R 1.24; two 16-row calls R 1.65).
  - **bf16** (HC mixers, PLE, block_inject): MLX's 32-row call equals 2 x 16 per row (D32).
  - **8-bit router / indexer and 4-bit small-N shapes** (shared expert, k / v, in_proj_a / b): two 16-row calls, because
    MLX's own 32-row call differs there (D32).
  - **24 GB (DENSE-N-RAM):** the same two 16-row native calls replace the unpack, which made dense-only 32 rows 181 ms.
- **Cache-dependent cores** (the GDN conv + recurrence + gated norm, and attention's SDPA) run as two 16-row calls in
  sequence.
  - Chunk 2 sees chunk 1's state and keys, exactly as the 1-row AR would.
  - The capture-commit stash concatenates both chunks' rows, so the commit replay is unchanged.
  - The lazy commit flushes first.
- **Experts** take one 32-row call through the widened gate (piece 1, BigMoE), so the union is read once. NAX6's per-row
  invariance at 32 rows is to be checked: the kernel is the same, but the pair grouping changes.
- **Estimate** at 45 GB and today's efficiency: dense 22.2 + experts ~54 (union 108.5 at NAX6-N's ~72 % of 285 GB/s) +
  cores and glue ~8-10 + misses = **~85-90 ms**, against ~130 for two 16-row checks. Kernel work then aims at ~65.
