- **Asked by:** BigMoE, Fri 04:4x. The orchestrator queued it for the Fri -> Sat night (about 01:00-10:00), after
  Leap's onebuild.
- **Track:** FAST. Whether P2 goes into a release is Kamen's call later.
- **The design:** that of docs/PREREG_p2gate_2026-11-11.md (the 24 GB P2 gate, PASS), at 45 GB. Its reference is a
  control arm run the same night, because no stored chat45 rows exist on this snapshot.

## What P2 is at 45 GB
- Prompts of at most 256 tokens skip the prefill and run in 16-row chunks as plain forwards under the decode arm
  (R57_P2_VERIFY=0). Longer prompts take the shipped prefill.
- **BigMoE's measurements (information):** its 45 GB A/B (bb61289: ABCCBA, a quiet lock, no heat freeze) on 12 IFEval
  prompts:
  - median first token 0.47 s, against 2.44 s for the shipped 45 GB chat (and 0.83 s for Strata);
  - tokens equal to the control's on 2 of 12, so it is LOSSY.
- **The 24 GB gate does not cover it:** that was 13-row chunks on the 24 GB card; this is 16-row chunks on the 45 GB
  chat.

## The arms (BigMoE b13abc6)
- **The control arm (tag c45):** the 45 GB chat as shipped: data/stack/chat45_env.txt line 2, git blob 40eee33e.... That
  is card_zs32's line plus R57_PFD=1, R57_PFD_V=4 and R57_PFD_AHEAD=1.
- **The P2 arm (tag p2_45):** data/stack/chat45_p2_env.txt line 2, git blob e4012e80.... It is the control's line plus
  exactly R57_P2=256, R57_P2_ROWS=16 and R57_P2_VERIFY=0. The runner checks that difference token by token.
- **Both arms:** C 256, on BigMoE's P3 snapshot (c477b60): screen data/r57/snap/p3/r57_screen_p3.py with its frozen deps
  data/r57/snap/frozen_p3. BigMoE gives the ref2 module's md5 as d05063fa.
  - The dated line before the start pins the screen's sha256, the snapshot, the .so and the code pin, from a dry run.
  - Both env lines set R57_QOM_SETS=humaneval,mbpp,ifeval,multi,lcb6,ifbench,gpqad, so QOM runs on IFBench and GPQA in
    both arms. The runner requires QOM optional uses on every kept run in those sets, as at the 45 GB card gates (m1b:
    19 of 19 per process).
  - With QOM, tokens depend on order and process composition. The m1b card arm's forward and reverse rows were
    identical on only 17 / 150 IFBench and 0 / 100 GPQA.
  - So both arms run the same keys in the same order and the same 20-prompt process split, and the comparison is paired
    by key.

## The keys (tools/p2_keys.json, sha256 c874dbc8..., as at 24 GB)
- **The P2 arm:** IFBench 150 (all of its prompts are <= 256 tokens) and GPQA Diamond's 67 prompts of <= 256 tokens, in
  the card gate's forward order, in run card_p2_45_fwd.
  - The 5 GPQA controls (258-269 tokens) go in their own run, card_p2_45_ctl.
- **The control arm:** the same 217 keys and the 5 controls, all in run card_c45_fwd, so it is the reference for both.
- **Not in the gate:** LCB v6, which has no prompt of <= 256 tokens, and IFEval, as at 24 GB.

## How it runs
- **The runner:** tools/day_runner63.sh, runner 62 (the 24 GB P2 gate's runner) with three switches:
  - CARD_P2=off, for the control arm: P2 must be off on every kept run (runs.json p2 empty), and its controls go in its
    one run. No verdict.
  - CARD_REF, the reference run: card_c45_fwd for the P2 arm.
  - CARD_FBLOB, the registered git blob of the env file, checked at the start.
  - Its code checks, manifests, gates and yields are runner 62's (runner 61's).
- **The chain:** tools/p2gate45_chain.sh.
  - It waits until Sat 01:00 and for anything else the orchestrator names.
  - Then it runs the control arm, then the P2 arm, only if the control arm's rows are complete.
  - Both arms have CARD_CUTOFF Sat 10:00. Either resumes with CARD_RESUME=1 if a later window is given.
- **Memory:** the env comments name no MEM, so the card runner's default of 47 applies: each process needs 51 GB of
  NO-SWAP free.
  - It runs only at night, with no 45 GB load by day.
  - Each process takes a share lock with MEM 47 in its reason and yields to another session's MEM job.
- **Estimate:**
  - The 45 GB card arms m1b and lcoh made 170-175K tokens on these 222 keys. Their 20-prompt GPQA processes took about
    10.5 min, and IFBench ones about 4-5 min.
  - So each arm takes about 1.3-1.6 h, 3-4 h for both with heat pauses.

## The lines (the card gate's rule, decision 4; tools/set_d4.py)
- **Per set:** the P2 arm against the control arm on the same keys. The paired delta must be above -5 points and the
  exact two-sided McNemar p at least 0.05; DIFFERS (HIGHER) passes.
  - IFBench on 150 keys, loose.
  - GPQA Diamond on 67 (SET_D4_N=67).
- **The control:** both arms run the 5 controls as their own 5-key process, in the same order. P2 must stay off on them
  (p2 = 0); otherwise the run is void.
  - **If the control arm is deterministic for identical input,** the P2 arm's 5 control rows must also be
    token-identical to the control arm's, or the gate FAILS. BigMoE answers this from its 45 GB A/B's repeated passes,
    and the dated line records the answer before the start.
  - **If it is not deterministic,** the controls' tokens are information only.
- **The gate PASSES** when both sets pass, the control holds, and both arms are valid.

## Validity (otherwise void)
- Both env files' blobs equal the registered ones, and the two env lines differ by exactly the three P2 keys.
- The runner's code checks pass, and both arms load the same modules (manifests equal across arms).
- **The P2 arm:** p2 > 0 on all 217 short keys and p2 = 0 on the 5 controls.
- **The control arm:** P2 off on every run.
- Every key has exactly one uncut run in each arm.

## Information (no verdict)
- token identity between the arms, per set;
- first-token time (runs.json pfs) per arm on the short prompts;
- whole decode;
- the lifetime peak (mem[6]) per arm, against the 45 GB line;
- heat pauses.

## Known limits
- **Power:** GPQA's 67 pairs give the test little power.
- **One order per arm,** in sequence: control first, then P2. With QOM, tokens also move with order, so token identity
  between the arms mixes P2's effect with that noise. The scores are paired by key.
- **Scope:** only the card's benchmarks. IFEval and other chat are not separately gated.

## Amendment 1b (Fri 2026-11-13 13:3x, before the resume): the control process's manifest check, and the resume
- **What happened:** the control arm started at 10:38 and made its 217 rows by 13:23. Every process passed its checks,
  including QOM engaged and P2 off.
  - Its 5-key control process (13:23-13:31, warm-up off as amendment 1 registers) was VOID by the manifest check:
    "outside modules: 40, compared 41 (all), equal: 40; DIFFERENT: ['qmm32']".
  - Its manifest has no qmm32 at all. Leap's qmm32 kernel is loaded by the warm-up prompt (gsm8k), which that process
    does not run.
  - So the void is a false alarm of runner 61's strict comparison: a module the process never loaded cannot change its
    output. No code changed; the chain's pinned trees were OK at 10:38.
- **The fix (tools/day_runner63.sh, sha256 251e7b03c4083e80...):** for the warm-up-off process, man_same compares in a new
  "subset" mode.
  - Every module that process loads must be in the reference manifest with the same sha, so a new or changed module
    still voids it.
  - A reference module it does not load is reported as "not loaded here".
  - Every other process keeps the strict "all" mode.
  - Tested on the real manifests: the void process passes "subset" with qmm32 not loaded, and still fails "all". fwd2
    passes "all".
- **The resume:**
  - The control arm runs with CARD_RESUME=1. Its 217 rows stand, its 5 controls rerun in a new warm-up-off process (the
    void process's rows were never appended), and its reference manifest is still its fwd1.
  - Then the P2 arm runs as registered, whose control process uses the same subset check.
  - Before the resume, the registered code is checked again (trees, screen, .so, blobs), as the chain does.
