## Reference check (each process, before any loop row)
The process re-decodes one reference row with the reference's own generator: HumanEval/27, n_prompt 81, 58 tokens,
crossing 128 keys at token 47. The `ref2` arm uses `decode._gen_ref2` with Leap's ref2 applied; the `stock` arm uses
`decode._gen`. Both run with PF1 on, as the reference rows did. If the row doesn't reproduce, the process decodes nothing
and the runner stops: **VOID**. The reference moved, not the loop, and that is diagnosed before any verdict.

## Verdicts (each arm on its own)
- **PASS** (NewIdeas' line): every token of all 36 prompts equals the reference row (equal token lists; the sha256 of
  each list is recorded).
- **FAIL:** any prompt differs. The result gives the first differing token, the check row that produced it, that row's
  logit gap from its argmax to the reference's token, and its top-2 gap.
- **VOID:** a reference check fails. **INCOMPLETE:** prompts missing at the deadline.
- **Consequences (NewIdeas'):** both PASS → the 16-row path is exact for REF2 adoption (decision 4's last step) and for
  the stock path. Any mismatch is a KILL for that arm's claim: a blocker, bisected with Leap.

**Prior, stated before any row:**
- The `ref2` arm is expected to pass (STEP 3k: 6/6).
- The `stock` arm can fail without a bug in the loop. Stock MLX kernels are not batch-invariant: a 1-row AR step runs
  other kernels than a 16-row check, which is why REF2 exists (R-40). Stock `generate_ar` also runs outside the verify
  scopes, where MTPLX's PLE gate lowers sigmoid differently (STEP 3t).
- So the expected failure mode for `stock` is a near-tie: a small logit gap at the first differing token. The gaps will
  show whether that is what happened.
- A `stock` FAIL doesn't change the `ref2` verdict.
