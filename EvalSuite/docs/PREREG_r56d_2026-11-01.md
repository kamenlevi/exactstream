## The change (model.py `block`)
- Our SparseMoeBlock patch replaces BigMoE's own block (`tier.install_block`), and it never handed the routing scores to
  BigMoE's tier call. So BIGMOE_TIER_COMBINE and BIGMOE_OOO could not engage in any EM.load-based run (Leap R-69D).
- Now, when the layer has BigMoE tiers and `bigmoe.tier` has COMBINE on with GLU 3c, the block sets
  `bm["tier"]["scores"]` before the switch and pops it after.
  - It uses the combined rows when the switch returns `[..., D]`, and our combine when it returns `[..., K, D]`.
  - Same ops and order otherwise: Leap's harness-only `_block_scores` (~/Leap/scripts/k69b_live.py), which R-69b
    passed with.
  - With COMBINE off the code runs exactly as before.
- Leap's R-69 tensor test: the fused combine and OOO's `combine_phase` are bitwise == our combine at 1-16 rows.

## Verdict (`tools/r56b.py ref2to_gate16` -> `results/r56d.txt`)
- **PASS needs all of these on all 36 prompts:**
  1. Every token equals the arm's AR and every kept row is bitwise equal, with all AR rows compared (R-56c's line).
  2. The AR's tokens equal `results/ref2t` (R-58's rows; otherwise VOID, as in R-56c).
  3. Every AR row hash and token equals R-56c's AR (`results/r56c/ar`, REF2-T without the switches). This shows the
     switches leave REF2-T's bits unchanged, not only the tokens.
  4. OOO ran every tier call: tier calls > 0 and OOO calls == tier calls, in the AR and in the loop of every prompt.
     Otherwise NOT ENGAGED: the test did not test the switch.
- **FAIL:** any token or row difference in 1 or 3 (the first bit and token differences are recorded).
- **Information:** tok/s (quiet mode; not an A/B with R-56c: other processes and times), kept per check, per-check
  path counts, lifetime footprint.
- **Not covered:** check widths 2-15. This harness always checks 16 rows, while the 45 GB default truncates (L1-14,
  t 0.3). Those widths are covered by R-69 (tensor, bitwise at 1-16) and R-69b (live, tokens equal on 4 prompts).
